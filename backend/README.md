# AI Trail Reporter — Backend

FastAPI + SQLAlchemy + Alembic backend, backed by local PostgreSQL with PostGIS and pg_trgm.

## Setup

1. Copy `.env.example` to `.env` and fill in your local PostgreSQL credentials.
   For Step 8 transcription, also set `SARVAM_API_KEY` (get one from
   https://dashboard.sarvam.ai) — see [Transcription (Step 8)](#transcription-step-8)
   below. For Step 9 LLM extraction, also set `ANTHROPIC_API_KEY` (get one from
   https://console.anthropic.com) — see [LLM structured extraction (Step
   9)](#llm-structured-extraction-step-9) below. Everything else in this backend
   works fine without either configured; only `POST .../transcribe` and
   `POST .../extract` need their respective key, and each reports a clean `503`
   if its key is missing. To use the admin dashboard (Step 18), also set
   `ADMIN_API_TOKEN` (any long random string) and, if the admin web app runs
   somewhere other than `http://localhost:5173`, `ADMIN_CORS_ORIGINS` — see
   [Admin dashboard (Step 18)](#admin-dashboard--content-curation--moderation-layer-step-18).
   Without `ADMIN_API_TOKEN` set, every `/api/v1/admin/*` route reports a
   clean `503` rather than being reachable unauthenticated.
2. Create and activate a virtual environment, then install dependencies:

   ```
   python -m venv .venv
   ./.venv/Scripts/pip install -r requirements.txt
   ```

3. Apply migrations (creates the postgis/pg_trgm extensions, core tables, and seeds
   example `knowledge_type_config` rows):

   ```
   ./.venv/Scripts/python -m alembic upgrade head
   ```

## Run

```
./.venv/Scripts/python -m uvicorn app.main:app --reload
```

Health check: `GET http://127.0.0.1:8000/health` — runs a real `SELECT 1` against the
database and reports connection status.

## API

All request/response bodies are JSON. Timestamps are ISO-8601 and must be
timezone-aware where noted.

### Create a guide

```
curl -X POST http://127.0.0.1:8000/api/v1/guides \
  -H "Content-Type: application/json" \
  -d '{"name": "Pemba Sherpa", "phone_number": "+9779800000001"}'
```

Returns the created guide, including its `id` (UUID) — use that `id` in the examples
below (shown as `<guide_id>`).

Optionally include `client_guide_id` (a UUID string generated by the caller, e.g. the
mobile app) to make this call **idempotent**: a repeat request with the same
`client_guide_id` returns the existing guide (HTTP 200) instead of creating a
duplicate (first call: HTTP 201). This is what the mobile sync engine uses — see
[`mobile/README.md`](../mobile/README.md#step-5--outbox-sync) for the full picture.

### Get a guide

```
curl http://127.0.0.1:8000/api/v1/guides/<guide_id>
```

### Update a guide's profile (Step 17)

Partial update of the two editable identity fields. Only the keys present in the
body are written, so a name-only update never blanks the phone number. Sending
`"phone_number": null` explicitly **clears** it.

```
curl -X PATCH http://127.0.0.1:8000/api/v1/guides/<guide_id> \
  -H "Content-Type: application/json" \
  -d '{"name": "Pemba Sherpa", "phone_number": "+9779800000002"}'
```

Accepts **only** `name` and `phone_number`. The mobile Profile screen's "About
you" note and profile photo are deliberately never sent here and have no server
representation — see [Explore voice notes & the guide profile (Step 17)](#explore-voice-notes--the-guide-profile-step-17).
A body with neither field is rejected with 422; an unknown guide is 404.

Naturally idempotent (it sets absolute values), so unlike the creation endpoints
it needs no client-generated id.

### Submit a GPS location

`recorded_at` is when the device captured the fix and **must include a UTC offset**
(naive timestamps are rejected). `received_at` is set by the server automatically.
Every call creates a new historical row — it never overwrites a previous location.

```
curl -X POST http://127.0.0.1:8000/api/v1/guides/<guide_id>/locations \
  -H "Content-Type: application/json" \
  -d '{"latitude": 27.9881, "longitude": 86.9250, "accuracy_meters": 15, "recorded_at": "2026-08-25T08:00:00+05:45"}'
```

Optionally include `client_location_id` (a UUID string generated by the caller) to
make this call **idempotent** — the same idempotency principle as `client_guide_id`
and `client_submission_id`:

- Same `client_location_id` + same data again → returns the existing sample
  (HTTP 200), no duplicate row created.
- Same `client_location_id` with **different** data → `409 Conflict` (the original
  sample is never silently overwritten).
- New `client_location_id`, or none supplied → creates a new sample (HTTP 201), the
  same unconditional behavior as before this field existed.

This is what the mobile GPS outbox sync uses — see
[`mobile/README.md`](../mobile/README.md#step-6--gps-location-capture--outbox-sync)
for the full picture.

### Get latest location

Returns the location with the newest `recorded_at` (not the most recently inserted
or received one). 404 if the guide doesn't exist, or a distinct 404 if the guide
exists but has no recorded locations yet.

```
curl http://127.0.0.1:8000/api/v1/guides/<guide_id>/locations/latest
```

### Location history

Paginated, newest `recorded_at` first.

```
curl "http://127.0.0.1:8000/api/v1/guides/<guide_id>/locations?limit=50&offset=0"
```

### Find nearby guides

Considers only each active guide's *latest* known location (older locations never
make a guide look nearby). Distance is computed by PostGIS (`ST_DWithin`/`ST_Distance`
on the `geography` column), not in Python.

```
curl "http://127.0.0.1:8000/api/v1/guides/nearby?latitude=27.9881&longitude=86.9250&radius_meters=5000"
```

### Create a known place

A known place is reference data — a named point (village, checkpoint, lodge, etc.)
that guide/observation coordinates can be resolved against.

```
curl -X POST http://127.0.0.1:8000/api/v1/locations \
  -H "Content-Type: application/json" \
  -d '{"name": "Everest Base Camp Checkpoint", "description": "Optional", "latitude": 27.9881, "longitude": 86.9250}'
```

### Get a known place

```
curl http://127.0.0.1:8000/api/v1/locations/<location_id>
```

### Find nearby known places

Nearest first, computed by PostGIS (`ST_DWithin`/`ST_Distance`). Returns an empty
list (not an error) when nothing is within range. `radius_meters` is capped by
`NEARBY_SEARCH_MAX_RADIUS_METERS` (default 50,000m).

```
curl "http://127.0.0.1:8000/api/v1/locations/nearby?latitude=27.9881&longitude=86.9250&radius_meters=5000"
```

### Resolve geographic context for a raw coordinate

Returns the nearest known place **only if** it's within
`GEOGRAPHIC_CONTEXT_RADIUS_METERS` (default 500m) of the coordinate; otherwise
`nearest_known_place` is `null`. Useful for testing coordinate → context resolution
independently of any guide or submission.

```
curl "http://127.0.0.1:8000/api/v1/geographic-context?latitude=27.9881&longitude=86.9250"
```

### Get a guide's current geographic context

Resolves context from the guide's latest location (by `recorded_at`). 404 if the
guide doesn't exist, or a distinct 404 if the guide has no recorded location yet.

```
curl http://127.0.0.1:8000/api/v1/guides/<guide_id>/context
```

### Ingest a submission (text note or voice metadata)

`capture_type` is `"note"` or `"voice"` (photo and other types are not implemented
yet). `client_submission_id` (a UUID string generated by the caller) is **required**
and makes this call idempotent, the same way `client_guide_id` does for guides:

- Same `client_submission_id` + same payload again → returns the existing submission
  (HTTP 200), no duplicate created.
- Same `client_submission_id` with **different** payload → `409 Conflict` (the
  original record is never silently overwritten).
- New `client_submission_id` → creates a new submission (HTTP 201).

Idempotency is enforced by a real unique constraint in PostgreSQL
(`submissions.client_submission_id`), not just an application-level check — safe even
under concurrent retries.

```
curl -X POST http://127.0.0.1:8000/api/v1/submissions \
  -H "Content-Type: application/json" \
  -d '{
        "guide_id": "<guide_id>",
        "client_submission_id": "b2b1a9c4-2a3e-4c1a-8f2a-2f7a9b1c0d3e",
        "capture_type": "note",
        "text_content": "Heavy snow near the bridge.",
        "submitted_at": "2026-08-25T08:00:00+05:45"
      }'
```

`submitted_at` is optional (defaults to server-received time) but, like other
timestamps in this API, must be timezone-aware if supplied.

For `capture_type: "voice"`, `text_content` must be **omitted or null** — a voice
submission's content is the audio itself, uploaded separately (see below). This is
metadata-only: the row exists (with `audio: null` in the response) before any audio
has actually been uploaded.

```
curl -X POST http://127.0.0.1:8000/api/v1/submissions \
  -H "Content-Type: application/json" \
  -d '{
        "guide_id": "<guide_id>",
        "client_submission_id": "b2b1a9c4-2a3e-4c1a-8f2a-2f7a9b1c0d3e",
        "capture_type": "voice",
        "submitted_at": "2026-08-25T08:00:00+05:45"
      }'
```

### Upload audio for a voice submission (Step 7)

Attaches durably-stored audio to a submission created with `capture_type: "voice"`
above. `multipart/form-data`, not JSON:

```
curl -X POST http://127.0.0.1:8000/api/v1/submissions/<submission_id>/audio \
  -F "file=@recording.m4a;type=audio/m4a" \
  -F "client_audio_id=1c9c4b2e-2f1e-4b1a-9b0a-2f3a9b1c0d3e" \
  -F "duration_seconds=7.3"
```

- `file` — the audio file. Validated against an explicit allow-list of content
  types/extensions the mobile app actually produces (`audio/m4a` + `.m4a`, plus a
  few equivalents), must be non-empty, and capped at
  `MAX_AUDIO_UPLOAD_SIZE_BYTES` (default 20 MiB — generous for a short voice note,
  not a general media upload limit). Rejected uploads never touch storage or the
  database.
- `client_audio_id` — a UUID string generated by the caller, **required**. A
  **second, distinct** stable id from `client_submission_id`: it makes the audio
  *attachment* step independently idempotent, since creating the submission and
  uploading its audio are two separate requests.
- `duration_seconds` — optional.

Idempotency, the same principle as everywhere else in this API but applied to a
two-step flow:

- No audio attached yet → saves the file, records the reference, returns the
  updated submission (HTTP 201).
- Audio already attached under the **same** `client_audio_id` → this is a retry of
  a request whose response was lost; returns the existing reference (HTTP 200)
  **without** writing another file.
- Audio already attached under a **different** `client_audio_id` → `409 Conflict`
  (this step does not support replacing an already-attached recording).
- Wrong submission (`capture_type` isn't `"voice"`) → `400`. Submission not found →
  `404`.

Race safety: the submission row is locked (`SELECT ... FOR UPDATE`) for the
duration of the attach, so two genuinely concurrent identical upload attempts are
fully serialized — verified with 5 real concurrent requests carrying the same
`client_audio_id` against a fresh submission: exactly one `201`, four `200`s, and
exactly one file written to disk (see mobile/README.md's Step 7 section for the
full verification results). The one known gap: if the process crashes between
writing the file to disk and committing the database row, that file is orphaned
(never referenced by any submission) — acceptable for this step, not a correctness
issue for the data that IS recorded.

The response never includes a filesystem path — only `content_type`,
`original_filename` (the client-supplied name, stored purely as display metadata —
never used as a filesystem path), `size_bytes`, and `duration_seconds`:

```json
{
  "...": "... (the usual submission fields) ...",
  "audio": {
    "content_type": "audio/m4a",
    "original_filename": "recording.m4a",
    "size_bytes": 58210,
    "duration_seconds": 7.3
  }
}
```

### Audio storage (Step 7)

Uploaded audio is written to a local filesystem directory
(`AUDIO_STORAGE_DIR`, default `var/audio_uploads/` under the backend's working
directory — see `app/services/storage/`), under a **server-generated** filename
(`{random-hex}.{extension}`). The client-supplied filename is never used as, or as
part of, a filesystem path — this rules out path traversal by construction, not by
sanitizing untrusted input (verified by uploading a file whose declared name was
`../../etc/passwd.m4a`: it was stored safely under the generated name, and the
malicious string only ever appears as inert display metadata in
`audio_original_filename`).

This is local filesystem storage for development/demo only, chosen because it
needs no new infrastructure (no MinIO/S3/object storage service) while the app
only runs against one backend process on one machine. `app/services/storage/base.py`
defines the storage interface (`AudioStorage.save()` / `.resolve_path()`); swapping
in an S3-compatible implementation for production is a matter of implementing that
same interface — nothing in the routes or `services/submissions.py` would need to
change. Not suitable as-is for a horizontally-scaled or multi-instance deployment
(each instance would only see files it personally wrote).

### Trigger/check transcription (Step 8)

Starts (or retries) transcribing a voice submission's uploaded audio via Sarvam
AI's Saaras speech-to-text API, or reports the current state without calling
Sarvam again if there's nothing new to do:

```
curl -X POST http://127.0.0.1:8000/api/v1/submissions/<submission_id>/transcribe
```

Always `200` with the current transcription state — `'processing'`/`'failed'` are
legitimate, honest outcomes of a successfully-handled request, not HTTP errors:

```json
{
  "id": "...",
  "submission_id": "...",
  "status": "completed",
  "transcript": "Heavy snow near the bridge.",
  "language_code": "en-IN",
  "language_probability": 0.95,
  "provider": "sarvam",
  "model": "saaras:v3",
  "mode": "codemix",
  "provider_request_id": "20260826_...",
  "error_message": null,
  "attempt_count": 1,
  "started_at": "...",
  "completed_at": "..."
}
```

- `404` — submission doesn't exist.
- `400` — submission isn't `capture_type: "voice"`, or it is but no audio has been
  uploaded yet.
- `503` — the server has no `SARVAM_API_KEY` configured.
- Already `completed` → returns the existing result immediately; **does not call
  Sarvam again**.
- Already `processing` (a concurrent request got there first) → returns the
  current `processing` state immediately; **does not start a second Sarvam call**.
- Otherwise (`pending` or `failed`) → makes one real Sarvam request, synchronously,
  and returns once it's done (this endpoint genuinely waits — see
  [Transcription (Step 8)](#transcription-step-8) for why).

### Check transcription status/result

Read-only — never triggers a Sarvam call.

```
curl http://127.0.0.1:8000/api/v1/submissions/<submission_id>/transcription
```

`404` if the submission doesn't exist, or if it does but transcription was never
started (no audio uploaded yet — nothing to check).

### Trigger/check LLM extraction (Step 9)

```
curl -X POST http://127.0.0.1:8000/api/v1/submissions/<submission_id>/extract
```

Works for **both** capture types:

- `note` — extracts directly from `Submission.raw_text`.
- `voice` — requires a `Transcription` with `status == 'completed'` first (call
  `POST .../transcribe` — see above). Extraction never triggers transcription
  itself and never calls Sarvam.

Returns the current `ExtractionRead`, including any persisted `observations`.
Possible outcomes, all `200` unless noted:

- `404` — submission doesn't exist.
- `400` — no usable source text yet: note has no/blank text, voice has no
  `Transcription` at all, or its `Transcription.status` is `pending`,
  `processing`, or `failed` (each gets its own specific message).
- `503` — the server has no `ANTHROPIC_API_KEY` configured.
- Already `completed` → returns the existing result (including its
  observations) immediately; **does not call the LLM again**.
- Already `processing` (a concurrent request got there first) → returns the
  current `processing` state immediately; **does not start a second LLM call**.
- Otherwise (`pending` or `failed`) → makes one real Claude request,
  synchronously, validates the result, persists zero or more observations, and
  returns once it's done — same synchronous-and-honest philosophy as
  transcription (see [When extraction starts](#when-extraction-starts) below).

### Check extraction status/result

Read-only — never triggers an LLM call.

```
curl http://127.0.0.1:8000/api/v1/submissions/<submission_id>/extraction
```

`404` if the submission doesn't exist, or if it does but extraction was never
started.

## Transcription (Step 8)

### Architecture

```
Mobile app
    |  (never talks to Sarvam directly -- see "Why Sarvam is backend-only" below)
    v
FastAPI backend
    |
    |  POST /api/v1/submissions/{id}/transcribe
    v
app/services/transcriptions.py  (orchestration: claim, lock, persist)
    |
    |  transcribe_audio(audio_bytes, filename, content_type)
    v
app/services/transcription/sarvam.py  (the ONLY file that imports the Sarvam SDK
    |                                   or knows its request/response shapes)
    v
Sarvam AI Saaras API (client.speech_to_text.transcribe, model="saaras:v3")
    |
    v
transcriptions.transcript / .language_code / .status = 'completed'  (PostgreSQL)
```

`app/services/transcription/sarvam.py` is the one place that imports the
`sarvamai` SDK, builds the request, and parses the response into a small
normalized `TranscriptionResult` (`transcript`, `language_code`,
`language_probability`, `request_id`, `model`, `mode`) — Sarvam-specific response
parsing does not leak into the orchestration layer, the routes, or the database
model.

### Complete audio → transcript flow

```
1. Find Submission (404 if missing).
2. Confirm capture_type == 'voice' (400 if not).
3. Confirm audio_storage_key is set (400 "audio not uploaded yet" if not).
4. Lock the Transcription row (SELECT ... FOR UPDATE) -- brief, released before
   any network call.
5. status == 'completed' -> unlock, return existing result. Stop.
6. status == 'processing' -> unlock, return current state. Stop. (Someone else
   is already handling this submission.)
7. status in ('pending', 'failed') -> claim it: status='processing',
   attempt_count += 1, started_at=now(), commit (releases the lock).
8. Resolve the stored audio through AudioStorage.resolve_path(storage_key).
9. File missing on disk -> mark 'failed', "Stored audio file is missing on the
   server.", stop.
10. Read the file's bytes, call Sarvam (client.speech_to_text.transcribe).
11. Provider/network/auth error, or an empty transcript -> mark 'failed' with a
    safe error message, stop.
12. Success -> persist transcript, language_code, language_probability, model,
    mode, provider_request_id; status='completed'; completed_at=now(); commit.
```

Never marks `'completed'` until the transcript is actually persisted in the same
transaction — there is no window where the API could report success before the
data is durably saved.

### Sync status vs. transcription status — two different questions

The mobile app's `sync_status` (`pending`/`uploading`/`uploaded`/`failed`, Step 5–7)
answers **"did the server receive the audio?"** `Transcription.status`
(`pending`/`processing`/`completed`/`failed`, this step) answers a completely
different question: **"did AI processing turn that audio into text?"** A voice
note can be `sync_status: 'uploaded'` and `transcription_status: 'pending'` at the
same time — that's the normal, expected state immediately after upload, not a bug.
These are two independent state machines on two different entities
(`local_capture.sync_status` on the phone; `transcriptions.status` on the server),
and nothing in this codebase conflates them.

### When transcription starts

Not automatic on upload, and not a background worker/queue (no Redis, no Celery —
deliberately, per this step's scope). Audio upload creates the `Transcription` row
as `'pending'` (atomically, in the same transaction as the audio attach — see
`services/submissions.py`), and transcription itself only actually runs when
something explicitly calls `POST .../transcribe`. That request is **synchronous**:
it waits for the real Sarvam call to complete (typically 1–5 seconds for a short
voice note) before responding. This was a deliberate simplicity choice for this
step's demo/local scope — a genuinely async/background version (so a slow Sarvam
call doesn't hold an HTTP request/thread open) is a natural, undone follow-up, not
implemented here per the step's explicit "no distributed task infrastructure"
constraint. The client (mobile or curl) is never left assuming transcription
happened automatically or instantly — it has to ask, and gets a truthful answer.

### Idempotency

`Transcription.attempt_count` and `status` are the only "did we already do this"
signals needed — there's no separate client-generated id here (unlike
`client_submission_id`/`client_audio_id`) because transcription isn't
client-initiated data creation, it's a server-side processing action on data that
already exists, keyed naturally by `submission_id` (which is already unique per
`Transcription` row). A `'completed'` transcription is never re-sent to Sarvam
under any circumstances in this step — retrying is an explicit, separate future
concept ("possibly re-transcription" per this step's own scope), not something
that happens implicitly.

### Concurrency

Two (or more) simultaneous `POST .../transcribe` calls for the SAME submission:
the `Transcription` row is locked with `SELECT ... FOR UPDATE` only for the brief
claim step (check status, set `'processing'`, commit) — **never held across the
Sarvam network call itself**, which would otherwise serialize unrelated reads
(like `GET .../transcription`) behind a multi-second external HTTP round trip.
Whichever request's lock-acquire+commit happens first wins and proceeds to call
Sarvam; every other concurrent request sees `'processing'` already set once it
gets the lock, and returns immediately without a second provider call.

**Verified with real concurrency, not just reasoned about**: 3 genuinely parallel
(`curl ... &` / `wait`) identical `POST .../transcribe` requests against a fresh
`'pending'` submission — exactly one reached Sarvam and became `'completed'`
(`attempt_count: 1`); the other two immediately returned `'processing'` with null
transcript fields. Confirmed directly in PostgreSQL afterward: `attempt_count`
was genuinely `1`, not `3`.

### What happens on provider failure

Every failure mode maps to `status='failed'` + a safe, specific `error_message` —
never a fabricated transcript, never a raw exposure of the API key or provider
internals:

| Cause | error_message |
|---|---|
| No `SARVAM_API_KEY` configured | (blocked earlier, `503`, no attempt recorded) |
| Sarvam rejects the key (real 403 observed in testing) | `"Sarvam API request failed (status 403)."` |
| Network/DNS/timeout failure | `"Could not reach the transcription service."` |
| Stored audio file missing from disk | `"Stored audio file is missing on the server."` |
| Sarvam returns an empty transcript | `"Transcription service returned an empty transcript."` |

A failed attempt leaves `status='failed'`, `attempt_count` incremented, and the
audio file completely untouched — the next `POST .../transcribe` call retries
from scratch (verified: a submission that failed due to an invalid key recovered
to `'completed'` on retry once a valid key was restored, `attempt_count` going
`1 -> 2`).

### Language / code-mix configuration

Two real, currently-supported parameters of the installed `sarvamai` SDK
(`client.speech_to_text.transcribe(..., mode=..., language_code=...)` — confirmed
by inspecting the actual installed SDK's method signature, not assumed from
docs):

- **`language_code="unknown"`** — auto-detect. There is no UI anywhere in this app
  that collects a per-recording language hint from the guide, so forcing a fixed
  `language_code` would be a guess this app has no basis for. Sarvam's own docs
  describe this value as "use when the language is not known; the API will
  auto-detect."
- **`mode="codemix"`** — per Sarvam's docs, produces "code-mixed text with English
  words in English and Indic words in native script." This matches the described
  real-world case directly: guides are expected to naturally mix Nepali and
  English while describing trail conditions, and `codemix` preserves that instead
  of forcing a single-language rewrite.
- **`model="saaras:v3"`** (configurable via `SARVAM_TRANSCRIPTION_MODEL`, per this
  step's explicit scope).

**Sherpa is explicitly NOT a supported `language_code`** in this SDK version — the
full list (`hi-IN`, `bn-IN`, `kn-IN`, `ml-IN`, `mr-IN`, `od-IN`, `pa-IN`, `ta-IN`,
`te-IN`, `en-IN`, `gu-IN`, `as-IN`, `ur-IN`, `ne-IN` (Nepali), `kok-IN`, `ks-IN`,
`sd-IN`, `sa-IN`, `sat-IN`, `mni-IN`, `brx-IN`, `mai-IN`, `doi-IN`) was read
directly from the installed SDK's method signature — nothing in this codebase
pretends Sherpa support exists.

### What is stored where

**PostgreSQL** (`transcriptions` table — see `app/db/models/transcription.py`):
`status`, `transcript` (the full text), `language_code`, `language_probability`,
`provider`, `model`, `mode`, `provider_request_id` (for correlating with Sarvam
support if ever needed), `error_message`, `attempt_count`, `started_at`,
`completed_at`. Deliberately **not** stored: the raw provider JSON response (the
normalized fields above are everything this app actually uses — see
`app/services/transcription/sarvam.py`).

**Filesystem** (`var/audio_uploads/`, unchanged from Step 7): the original audio
file — transcription reads it, never modifies, moves, or deletes it. A submission
keeps its audio file regardless of transcription success or failure.

### Database schema decision: separate `Transcription` entity, not columns on `Submission`

Considered fields directly on `Submission` (fewer tables) vs. a separate
`Transcription` table (this codebase's actual choice). `Submission` already means
"what the guide submitted" — a stable, submission-lifecycle concept (Step 5–7).
Transcription is a genuinely different lifecycle layered on top: its own
retry/attempt history, its own provider metadata, its own errors, and — per this
step's own stated future direction — possibly re-transcription and human review
later. Bolting all of that onto `Submission` would mean every future AI-processing
concern (this step's transcription, a later structured-extraction step, etc.)
accumulates as more unrelated columns on one increasingly overloaded table. A
separate table keeps `Submission` exactly as clean as Step 7 left it and gives
transcription its own natural home — `submission_id` is unique for this step (one
active transcription per submission, retried in place by mutating the same row)
rather than an attempt-history table, because nothing yet needs multiple
historical attempts to coexist; loosening that uniqueness constraint later, if
full attempt history becomes genuinely necessary, is a small, additive migration.

### Why Sarvam is called only from the backend

The mobile app never holds `SARVAM_API_KEY` — it isn't in mobile source, `app.json`,
any `EXPO_PUBLIC_*` variable, or mobile's own `.env` (confirmed: zero references
to "sarvam" anywhere in `mobile/`, case-insensitive, across this entire codebase).
The mobile app only ever calls this backend's own
`POST /api/v1/submissions/{id}/transcribe`; the backend is the only thing that
holds the key, reads it once from environment configuration
(`app/core/config.py`), and never logs, returns, or echoes it anywhere — every
error path returns a short, safe message (see the failure-mode table above), never
provider request/response internals that could contain it.

## LLM structured extraction (Step 9)

### Architecture

```
Submission (note text_content) ----+
                                    |
Submission (voice) -> Transcription.transcript (Step 8, must be 'completed')
                                    |
                                    v
                app/services/source_text.py  (resolve_source_text -- ONE
                |                              normalized text abstraction;
                |                              extraction never knows whether
                |                              the source was a note or voice)
                v
app/services/extractions.py  (orchestration: claim, lock, persist)
                |
                |  extract_observations(source_text, allowed_types, nearest_place)
                v
app/services/extraction/anthropic_provider.py  (the ONLY file that imports the
                |                                 anthropic SDK)
                v
Claude (client.messages.create, tool_choice forced to record_observations)
                |
                v
app/services/extraction/validation.py  (Pydantic + allowed-knowledge-type check
                |                        -- NEVER trusts provider output directly)
                v
extractions.status = 'completed'; observations rows  (PostgreSQL, one commit)
```

`app/services/extraction/anthropic_provider.py` is the one place that imports
the `anthropic` SDK, builds the request, and returns the raw tool-call `input`
dict — Anthropic-specific request/response handling does not leak into the
orchestration layer, the routes, or the database model. `app/services/
extraction/prompt.py` builds the system prompt and JSON-schema tool
definition and imports nothing from the SDK, so provider transport and domain
prompt design stay in separate files (per this step's own requirement).

### Complete source text → LLM → observations flow

```
 1. Find Submission (404 if missing).
 2. Get-or-create the Extraction row, locked (SELECT ... FOR UPDATE) -- lazily,
    on first POST .../extract (unlike Transcription, there's no "audio arrived"
    system event to eagerly create this row against; see "When extraction
    starts" below).
 3. status == 'completed' -> unlock, return existing result (incl. persisted
    observations). Stop.
 4. status == 'processing' -> unlock, return current state. Stop.
 5. status in ('pending', 'failed') -> resolve_source_text(submission). If it
    raises (no text / transcription missing / pending / processing / failed /
    empty transcript), unlock with NO status change and propagate a specific
    400. The row is left exactly as it was -- still retryable once source text
    exists.
 6. Claim it: status='processing', attempt_count += 1, started_at=now(),
    commit (releases the lock).
 7. Load active KnowledgeTypeConfig rows from PostgreSQL (the ONLY source of
    allowed knowledge_type values -- see "Knowledge type configuration" below).
    None active -> mark 'failed', stop.
 8. Resolve geographic context: submission's own lat/lon if present, else the
    guide's latest GuideLocation AT OR BEFORE submitted_at (never a later,
    closer-but-wrong ping; never fabricated if none exists).
 9. Call Claude with the resolved source text, allowed knowledge types, and
    (if resolved) nearest-known-place context, tool_choice forced to
    record_observations.
10. Provider/network/auth error, or no tool_use block returned -> mark
    'failed' with a safe error message, stop.
11. Validate the raw tool output: Pydantic shape (knowledge_type: str, value:
    dict, confidence: 0..1, evidence: non-empty str) AND every knowledge_type
    is in the allowed set loaded in step 7. ANY violation -> mark 'failed',
    persist NOTHING (rejected as a whole, not partially). Stop.
12. Success -> build one Observation row per validated candidate (submission_id,
    guide_id, knowledge_type_id, resolved lat/lon/geog, value, confidence,
    evidence, observed_at = submission.submitted_at -- NEVER extraction time);
    set extraction status='completed', model, completed_at; ONE commit
    persists the observations and the 'completed' status together.
```

Never marks `'completed'` until observations are actually persisted in the
same transaction as the status change — there is no window where the API
could report success before the data is durably saved, and a crash between
"validated" and "committed" leaves the row still `'processing'` (retryable
later) rather than silently losing data.

### Sync status vs. transcription status vs. extraction status — three different questions

A **third**, independent state machine, alongside the two from Step 5–8. The
mobile app's `sync_status` answers *"did the server receive this?"*
`Transcription.status` answers *"did AI turn audio into text?"*
`Extraction.status` (`pending`/`processing`/`completed`/`failed`, this step)
answers a third, different question: **"did LLM processing turn the resolved
source text into structured observations?"** A voice note can simultaneously be
`sync_status: 'uploaded'`, `transcription_status: 'completed'`, and
`extraction_status: 'pending'` — that's the normal, expected state right after
transcription finishes, not a bug. Nothing in this codebase conflates any of
the three.

### When extraction starts

Not automatic — for **either** capture type. A note's text is available the
moment it's synced, but extraction still only runs when something explicitly
calls `POST .../extract`; a voice submission additionally requires a separately
completed, separately-triggered transcription first (Step 8's flow is
untouched — extraction never calls Sarvam). No background worker/queue (no
Redis, no Celery — deliberately, matching Step 8's scope). The request is
**synchronous**: it waits for the real Claude call to complete (typically 1–4
seconds for a short field report) before responding, for the same reasons
transcription does — this is a deliberate simplicity choice for this step's
demo/local scope, not a permanent architecture.

### Idempotency

Same principle as Transcription (Step 8): `Extraction.attempt_count` and
`status` are the only "did we already do this" signals needed. There's no
separate client-generated id because extraction isn't client-initiated data
creation — it's a server-side processing action, keyed naturally by
`submission_id` (unique per `Extraction` row). Unlike Transcription (whose row
is pre-created eagerly when audio is attached), the Extraction row is
get-or-created lazily on the first `POST .../extract` — a genuine "two
concurrent first-ever triggers" race is possible here, so row *creation*
itself uses the same IntegrityError-catch-and-refetch pattern as
`create_or_get_submission`, in addition to (not instead of) the `SELECT ...
FOR UPDATE` claim step used for the status transition.

### Concurrency

Identical strategy to Transcription: the `Extraction` row is locked with
`SELECT ... FOR UPDATE` only for the brief claim step — never held across the
LLM network call. Whichever request's lock-acquire+commit happens first wins
and proceeds to call Claude; every other concurrent request sees `'processing'`
already set once it gets the lock, and returns immediately without a second
provider call.

**Verified with real concurrency, not just reasoned about**: 3 genuinely
parallel (`curl ... &` / `wait`) identical `POST .../extract` requests against
a fresh `'pending'` note submission — exactly one reached Claude and became
`'completed'` (`attempt_count: 1`, 2 observations persisted); the other two
immediately returned `'processing'` with an empty observations list. Confirmed
directly in PostgreSQL afterward: `attempt_count` was genuinely `1` and exactly
2 observation rows existed for that submission — no duplicates from the race.

### What happens on provider failure / invalid output

Every failure mode maps to `status='failed'` + a safe, specific
`error_message` — never fabricated observations, never a raw exposure of the
API key or provider internals, and nothing partially persisted:

| Cause | error_message |
|---|---|
| No `ANTHROPIC_API_KEY` configured | (blocked earlier, `503`, no attempt recorded) |
| Claude rejects the request (real 400 observed in testing — see note below) | `"LLM extraction request failed (status 400)."` |
| Network/DNS/timeout failure | `"Could not reach the LLM extraction service."` |
| No active `knowledge_type_config` rows | `"No active knowledge types are configured on the server."` |
| Response has no tool_use block at all | `"LLM extraction service did not return structured output."` |
| Output fails Pydantic shape validation (mocked in testing — missing required field) | `"LLM output failed schema validation (N error(s))."` |
| Output uses a knowledge_type outside the allowed set (mocked in testing) | `"LLM returned an unknown knowledge_type: '...'"` |

The real `400` observed during development was **not** a transient provider
error: an earlier version of the tool schema requested Anthropic's `strict:
True` validation mode, which rejects any object-typed schema field that
doesn't explicitly set `additionalProperties: false`. `value` is intentionally
open-ended JSON (the LLM chooses its own field names per observation, per this
step's spec), which is fundamentally incompatible with `strict` mode's closed-
schema requirement — confirmed directly against the real API, not assumed. The
fix was to drop `strict: True` and rely on
`app/services/extraction/validation.py`'s Pydantic validation as the actual
safety boundary (which the spec requires regardless of provider-side
guarantees) — the JSON schema now only *steers* the model, it doesn't gate
correctness by itself. See the docstring in `app/services/extraction/prompt.py`
for the full account.

A failed attempt leaves `status='failed'`, `attempt_count` incremented, and no
observation rows persisted — the next `POST .../extract` retries from scratch.
**Verified with a real recovery, not just reasoned about**: a submission that
failed 3 times in a row under mocked failure conditions (unknown
knowledge_type, malformed shape, simulated network failure) recovered to
`'completed'` on the very next real, unmocked retry, `attempt_count` going
`3 -> 4`, with zero observation rows left behind by any of the 3 failed
attempts.

### Knowledge type configuration

The LLM is never allowed to invent a `knowledge_type`. Each extraction request
loads the currently `active` rows from `knowledge_type_config` (PostgreSQL —
the sole source of truth, never a hardcoded list in application code) via
`app/services/knowledge_types.py`, and:

1. Their `knowledge_type` values populate the tool schema's `knowledge_type`
   enum, steering the model toward only those values.
2. **Independently and unconditionally**, `app/services/extraction/
   validation.py` re-checks every returned `knowledge_type` against that same
   loaded set and rejects the whole response (not just the offending item) if
   any value isn't in it — because the model returning something outside the
   schema's `enum` is possible without `strict` mode (see above), and provider
   output must never be trusted directly regardless of what the schema asked
   for.

`display_name` for each allowed type is also passed into the prompt as a
one-line human-readable hint (e.g. `snow_ice: Snow / Ice Conditions`) so the
model has some sense of what each type means beyond the raw slug — but the
`value` object's internal shape is deliberately left to the model's judgement
per observation (see "Structured output validation" below for why).

### Structured output validation

`app/services/extraction/anthropic_provider.py` forces `tool_choice` to the
`record_observations` tool, so Claude's response is guaranteed to be a
structured tool call — never free text needing separate parsing. The raw
`input` dict from that tool call is treated as **completely untrusted** until
it passes `app/services/extraction/validation.py`:

- Pydantic validates the shape: `observations` is a list; each item has
  `knowledge_type: str`, `value: dict`, `confidence: float` (0.0–1.0
  inclusive), `evidence: str` (non-empty).
- Every `knowledge_type` is checked against the active-types set loaded from
  PostgreSQL for *this* request (see above).
- A single invalid item fails the **entire** response — nothing is partially
  persisted from a response that's part-valid, part-broken.
- An empty `observations` list is a **valid, successful** result (`status`
  still becomes `'completed'`) — confirmed in real testing: a genuinely
  content-free note text produced a real Claude response with zero
  observations, correctly stored as a `'completed'` extraction with no
  `Observation` rows.

`confidence` is stored as-is under the name it has — **model extraction
confidence**, not a claim about ground truth. Nothing in this codebase treats
it as objective certainty.

### Geographic context — attached programmatically, never by the LLM

The LLM never outputs coordinates, and the prompt explicitly instructs it not
to infer a specific place from general knowledge (rule 9 in the system
prompt, `app/services/extraction/prompt.py`). All geography on a persisted
`Observation` comes from actual PostGIS/database data, resolved in
`app/services/extractions.py::_resolve_observation_coordinates` *before* the
LLM is even called:

1. If the submission itself has `latitude`/`longitude` set, use those.
2. Otherwise, use the guide's latest `GuideLocation` **at or before**
   `submitted_at` (a new helper,
   `guide_locations.get_latest_location_at_or_before` — deliberately NOT
   "whatever the guide's latest location is right now," since extraction can
   run long after the report was made; using the guide's *current* location
   would misattribute where the condition was actually observed).
3. If neither exists, the observation's `latitude`/`longitude`/`geog` are left
   `NULL` — never fabricated.

If coordinates were resolved, `resolve_geographic_context` (the same Step-1
service `GET /api/v1/geographic-context` uses) finds the nearest known
`Location` within `GEOGRAPHIC_CONTEXT_RADIUS_METERS`, if any, and its name is
passed into the prompt as **background context only** ("Approximate location
context: near 'X' (~120m away). ... do not output coordinates or place names
yourself.") — informational framing for the model, never a value it can set.

**Verified in real testing**: a note submitted with a real prior `GuideLocation`
sample recorded 2 hours earlier produced observations whose `latitude`/
`longitude` exactly matched that `GuideLocation` row (not the guide's
non-existent "current" location, not a hallucinated coordinate) — confirmed
directly in PostgreSQL.

### Observed timestamp — the report's own time, never extraction time

Every persisted `Observation.observed_at` is set to `submission.submitted_at`
— when the guide actually made the report — never `datetime.now()` at
extraction time. Extraction can run seconds or days after a submission was
made (it's an explicit, on-demand action); using the current time would
misdate every observation by however long it sat unextracted. Verified in
testing: a submission's `submitted_at` and every one of its resulting
observations' `observed_at` matched exactly, even though extraction itself ran
minutes later.

### What is stored where

**PostgreSQL, `extractions` table** (`app/db/models/extraction.py`): `status`,
`provider`, `model`, `error_message`, `attempt_count`, `started_at`,
`completed_at`. Deliberately **not** stored: the raw provider JSON response, or
the prompt itself (both are reconstructible from code + the persisted
observations; storing them would just be an unused duplicate of information
that's already meaningfully captured).

**PostgreSQL, `observations` table** (`app/db/models/observation.py`, extended
this step with one new nullable `evidence: Text` column — see "Database schema
decisions" below): `submission_id`, `guide_id`, `knowledge_type_id`,
`latitude`/`longitude`/`geog`, `value` (JSONB), `confidence`, `evidence`,
`observed_at`. This is the actual product output of this step — durable,
structured, queryable knowledge.

**Nothing new on the filesystem.** Extraction reads only PostgreSQL data
(resolved source text, active knowledge types, guide locations) — it never
touches `var/audio_uploads/`.

### Database schema decisions

**Separate `Extraction` entity, not columns on `Submission` or `Transcription`**
— for the exact same reasoning Step 8 gave for `Transcription` itself (see
above): a genuinely different lifecycle (its own retries/errors/provider
metadata), and the natural home for a later re-extraction concept, without
`Submission` (or `Transcription`) accumulating more unrelated AI-processing
state. `submission_id` is unique — one row per submission, retried in place —
matching `Transcription`'s convention rather than inventing a different one.

**Lazy creation, unlike `Transcription`'s eager creation** — `Transcription` is
created the moment audio is attached, because "audio arrived" is a real system
event worth tracking immediately. There is no equivalent event for extraction:
both notes and voice submissions only become extractable through an explicit
user action, so creating the row any earlier would just be dead state with
nothing meaningful to report. See "Idempotency" above for how this changes the
concurrency-safety code (get-or-create needs its own race handling, not just
the claim step).

**One new column on `Observation`: `evidence: Text`, nullable** — the smallest
schema change that satisfies this step's explicit requirement that every
observation carry short, source-grounded evidence. Considered folding
`evidence` into the existing `value` JSONB blob instead of a new column, but
`confidence` (a sibling concept — "how sure is the extractor") already gets its
own dedicated, directly-queryable column; `evidence` follows the same
established pattern rather than introducing a second, inconsistent way to
attach extraction metadata to an observation. Nullable at the DB level only
for migration safety (older rows, if any existed, wouldn't have one) — every
observation this step's pipeline creates always sets it.

**No new `location_id` foreign key on `Observation`** — considered linking each
observation to a specific known `Location` row (in addition to raw
lat/lon/geog) for a human-readable place label, but decided against it:
`Observation` already stores a raw coordinate (needed for spatial queries like
`ST_DWithin` against each knowledge type's own
`geographic_relevance_radius_meters` — a later step's concern, not this one's),
and "which known place is nearest" is fully re-derivable from that coordinate
at read time via the exact same `resolve_geographic_context` service already
used elsewhere. Adding a stored `location_id` would just be a denormalized,
potentially-stale duplicate of something already cheaply queryable — not
"required for correct traceability" in the sense this step's spec asked for.

**No new fields on `KnowledgeTypeConfig`** — considered adding a
`description`/`extraction_schema_hint` column so the prompt could give
richer per-type guidance, but `KnowledgeTypeConfig` already has
`display_name`, which is enough of a human-readable hint combined with the
system prompt's general instructions for `value`'s shape (see "Structured
output validation" above for why `value` is deliberately open-ended rather
than a fixed per-type schema). Not touching this table also means Step 9
doesn't risk destabilizing the freshness/relevance policy fields Step 1
established there.

### Why the LLM provider is called only from the backend

The mobile app never holds `ANTHROPIC_API_KEY` — it isn't in mobile source,
`app.json`, any `EXPO_PUBLIC_*` variable, or mobile's own `.env`. The mobile
app only ever calls this backend's own `POST /api/v1/submissions/{id}/extract`;
the backend is the only thing that holds the key, reads it once from
environment configuration (`app/core/config.py`), and never logs, returns, or
echoes it anywhere — every error path returns a short, safe message (see the
failure-mode table above), never provider request/response internals that
could contain it.

## Knowledge state (Step 10)

Deterministic freshness/staleness/gap detection — no LLM involved. Answers:
*"for this geographic point and point in time, for each active knowledge type,
what is the current knowledge state?"*

```
GET /api/v1/knowledge-state?latitude=...&longitude=...&evaluation_time=...
GET /api/v1/guides/{guide_id}/knowledge-state?evaluation_time=...
```

The guide endpoint resolves the guide's latest `GuideLocation` (by
`recorded_at`, never insertion order — same rule as `/guides/{id}/context`)
and evaluates at that exact coordinate; `404` if the guide has no location yet
(identical error text to `/context` and `/locations/latest`). Both endpoints
share one core function, `app/services/knowledge_state.py::evaluate_knowledge_state`.

**Per knowledge type** (every `active` row in `knowledge_type_config` — inactive
rows never appear): find the latest `Observation` of that type within THAT
type's own `geographic_relevance_radius_meters` (PostGIS `ST_DWithin`, reusing
`app/db/geo.py::make_point` — never Python distance math), then classify by
comparing its `observed_at` against THAT type's own `freshness_window_hours`
— never one global threshold:

- **missing** — no geographically-relevant observation exists at all.
- **fresh** — `evaluation_time <= observed_at + freshness_window_hours` (the
  boundary itself counts as fresh — inclusive, not strict).
- **stale** — `evaluation_time > observed_at + freshness_window_hours`.

`evaluation_time` is a required, explicit parameter of the core service (never
hidden behind an internal `now()`), defaulting only at the API boundary —
so the identical stored data can be replayed at different evaluation times.
Confidence is **not** used to filter or weight anything here — there's no
existing configured confidence policy, and this step doesn't invent one.

**Gap summary**: `fresh_count` / `stale_count` / `missing_count` /
`gap_count` (`stale_count + missing_count`), plus a pre-filtered `gaps` list
(the non-fresh subset) carrying each gap's `safety_critical` / `default_priority`
/ radius / window straight from `knowledge_type_config`, so a later ranking
step doesn't need to re-query this metadata.

**Index**: `ix_observations_knowledge_type_id_observed_at` (new this step —
`observations` had no index on `knowledge_type_id` at all before; Postgres
doesn't auto-index FK columns) supports the `WHERE knowledge_type_id = ?
ORDER BY observed_at DESC LIMIT 1` pattern this engine runs once per active
type per evaluation. **Verified with `EXPLAIN ANALYZE` against real data**: at
the current small dataset size (a dozen test rows), the planner chose the
existing GiST `idx_observations_geog` index for the `ST_DWithin` filter and
sorted the tiny remaining result set in memory rather than using the new
btree index — a correct, honest planner choice at this scale, not a sign the
index is wrong; it becomes the more attractive plan as each knowledge type
accumulates hundreds+ of observations globally.

Tested against real PostgreSQL: independent per-type freshness (two types,
two different windows, one fresh/one stale at the same evaluation_time);
missing when no relevant observation exists; geographic relevance correctly
preferring an older-but-inside-radius observation over a newer-but-outside
one; the same distance being relevant for one type's radius and irrelevant
for another's; the freshness boundary exactly at/just-before/just-after;
identical data reclassified under a different `evaluation_time`; latest
selected by `observed_at` even when inserted out of order; the guide endpoint
producing byte-identical `knowledge_state` to the point endpoint at the same
coordinate; the no-location 404; and inactive types being excluded (verified
by temporarily flipping a real config row and restoring it).

## Gap ranking & guide selection (Step 11)

Deterministic decision-making on top of Step 10 — no LLM involved. Answers:
*"at this moment, what information should the system try to collect next, and
which guide is the best available guide to ask?"*

```
GET /api/v1/knowledge-decisions?latitude=...&longitude=...&evaluation_time=...
GET /api/v1/guides/{guide_id}/knowledge-decisions?evaluation_time=...
```

Both reuse `app/services/knowledge_state.py::evaluate_knowledge_state`
**unchanged** — this step never recomputes freshness/staleness/missing itself,
it only ranks Step 10's `gaps` and finds candidate guides for each one.

**Gap ranking** (`app/services/knowledge_decisions.py`) orders every gap by an
explicit tuple (each component fully dominates the next — not a blended
score):

1. `safety_critical` (from `knowledge_type_config`) — safety-critical first.
2. `state` — `missing` ranks ahead of `stale`. **Application-level rule, not
   a database policy**: no observation at all is treated as a stronger gap
   than stale-but-present evidence.
3. `default_priority` — higher first. **`default_priority`'s direction is not
   documented anywhere in this codebase** (inspected: model, seed data,
   README — no comment either way); this step makes one explicit,
   centralized interpretation (`_HIGHER_DEFAULT_PRIORITY_IS_MORE_IMPORTANT =
   True` in `knowledge_decisions.py`) rather than guessing silently.
4. Staleness severity — `evaluation_time - freshness_expires_at` in hours
   (reuses Step 10's already-computed `freshness_expires_at`; 0.0 for
   `missing`, where the concept doesn't apply).
5. `knowledge_type` name, ascending — final deterministic tie-breaker.

**`aging_threshold_hours` is deliberately NOT used** — inspected and confirmed
it has no defined semantics anywhere in the codebase (see Step 10's Notes
entry too); this step doesn't invent behavior for an undocumented field.

**Guide candidate selection**, per ranked gap: reuses
`app/services/guide_locations.py::find_nearby_guides` **unchanged** — it
already does exactly what's needed (active guides only, each guide's single
latest location via `DISTINCT ON ... ORDER BY recorded_at DESC`, PostGIS
`ST_DWithin`/`ST_Distance` against the gap's target coordinate, using that
knowledge type's own `geographic_relevance_radius_meters`). Ranking on top of
that small, already-filtered result is plain Python — no new SQL, no
Haversine math: `(distance_meters ascending, location_age_hours ascending,
guide_id ascending)`. `selected_guide` is candidate rank 1, or `null` if the
list is empty — **never fabricated**.

Gap `target_latitude`/`target_longitude` are modeled per-gap (not just once at
the top level) — in this step's only call pattern every gap shares the same
target (the request's own coordinate), but the shape is ready for a future
step evaluating gaps at genuinely different locations.

**No new migration.** `EXPLAIN ANALYZE` on the real guide-candidate query
confirmed the existing `ix_guide_locations_guide_id_recorded_at` (composite
btree) and `idx_guide_locations_geog` (GiST) indexes already structurally fit
this query's shape; at the current tiny dataset the planner chose a seq scan
+ in-memory sort/dedup instead of either index — the same honest small-data
planner behavior documented for Step 10, not a sign anything is missing.

Tested against real PostgreSQL: the full safety→missing/stale→priority→
staleness precedence chain (verified end-to-end with 4 gaps of differing
policy); a fully-tied pair broken deterministically by knowledge_type name,
with repeated calls proving stability; a guide's stale-but-nearby location
correctly ignored in favor of its genuinely latest (far-away) one; 3+ active
guides correctly ranked by distance-then-recency with an out-of-order-inserted
latest location resolved correctly; an inactive guide excluded despite being
geographically closest; zero relevant candidates producing a real `null`
`selected_guide`; identical stored data producing a different ranked-gap set
under two different `evaluation_time` values; and both endpoints exercised
live, including the guide-scoped one (which can list the requesting guide
itself as a candidate for a gap near their own position — this endpoint
answers "what's the decision state around me," not "what should I be asked").
Full regression across health/guides/locations/geographic-context/
knowledge-state/submissions/transcriptions/extractions — no regressions.

## Question generation & assignment (Step 12)

Takes a ranked knowledge gap (Step 10 + Step 11, reused entirely unmodified)
and turns it into a persisted, natural-language question for a trek guide,
using Claude — the first place in this codebase an LLM call produces
guide-facing text rather than structured data extraction.

```
POST /api/v1/questions
GET  /api/v1/questions/{question_id}
GET  /api/v1/guides/{guide_id}/questions
```

### Generate (or retry/replay) a question

```
curl -X POST http://127.0.0.1:8000/api/v1/questions \
  -H "Content-Type: application/json" \
  -d '{
    "latitude": 27.7172, "longitude": 85.3240,
    "knowledge_type": "snow_ice",
    "client_request_id": "5c1f7e0a-9c2b-4f7e-8a1e-2b6a7c9d1e3f"
  }'
```

Identifies the gap the same way Step 10/11's own point-based endpoints do — a
coordinate + optional `evaluation_time` — plus `knowledge_type`, which of the
CURRENT ranked gaps at that point to generate for. Always returns `200` with
the current `QuestionRead` — `processing`/`failed` are legitimate, honest
states of a successfully-handled request, not HTTP-level errors (same
philosophy as `POST .../transcribe` and `POST .../extract`):

- `400` — `knowledge_type` doesn't match any active `knowledge_type_config`
  row, OR it isn't currently a gap (missing/stale) at that coordinate/time
  (it's fresh, or nothing configured produces it) — re-verified server-side
  every time, never trusted from a client-supplied gap snapshot.
- `409` — `client_request_id` was already used with a different
  `knowledge_type`/coordinate.
- `503` — the server has no `ANTHROPIC_API_KEY` configured.
- Already `generated` → returns the existing question (and its current
  assignment) immediately; **does not call the LLM again**.
- Already `processing` → returns the current `processing` state immediately;
  **does not start a second LLM call**.
- Otherwise (`pending` or `failed`) → makes one real Claude request,
  synchronously, validates the result, persists it, assigns it if a guide is
  currently relevant, and returns once it's done.

### Question lifecycle

A **fourth** independent state machine (`app/db/models/question.py`),
alongside mobile `sync_status`, `Transcription.status` (Step 8), and
`Extraction.status` (Step 9). Answers *"did LLM processing turn a knowledge
gap into a usable question?"*:

- `pending` — row created (a real gap was confirmed at creation time),
  generation not yet attempted.
- `processing` — an LLM request is currently in flight.
- `generated` — a validated `question_text` was produced and persisted.
- `failed` — the last attempt failed (provider error, invalid output, OR the
  underlying gap resolved before/during generation — see Revalidation below);
  retryable via `POST /api/v1/questions` with the same `client_request_id`.

### Two more state machines: assignment status, and how all five relate

A **fifth**, deliberately SEPARATE state machine
(`app/db/models/question_assignment.py`) answers a different question again:
*"what is the guide doing with this question?"* — `assigned` / `active` /
`completed` / `cancelled`. **Only `assigned` is ever actually set by any code
in this step** — `active`/`completed`/`cancelled` are defined for schema
forward-compatibility (a future answer workflow, per this step's own scope)
but no transition logic exists yet. A question can be `generated` with **no**
assignment at all (see "No guide available" below) — `Question.status` and
`QuestionAssignment.status` are never conflated, exactly like every prior
pair of independent state machines in this codebase:

| Layer | State machine | Answers |
|---|---|---|
| Mobile | `sync_status` | Did the server receive this? |
| Backend | `Transcription.status` (Step 8) | Did AI turn audio into text? |
| Backend | `Extraction.status` (Step 9) | Did AI turn text into observations? |
| Backend | `knowledge_state` (Step 10, computed live) | Is nearby knowledge fresh/stale/missing? |
| Backend | `Question.status` (Step 12) | Did AI turn a gap into a question? |
| Backend | `QuestionAssignment.status` (Step 12) | What is the assigned guide doing with it? |

### Revalidation: knowledge state is live and can change mid-flight

Because knowledge state is computed live (Step 10) directly from
`observations`, it can change between when a question's generation starts and
when it finishes — a new observation could arrive while Claude is still
"thinking." `generate_question` checks the gap **twice**:

1. Immediately before claiming the attempt (cheap guard — mostly avoids
   spending a real LLM call on an obviously-already-resolved retry).
2. Immediately after the LLM call returns, right before
   persisting/assigning — using the **freshly re-evaluated** `selected_guide`
   too, not the pre-call one, since a guide could also have moved during the
   call.

If the gap is gone at check 2, the attempt is discarded: `status='failed'`
with an honest `error_message`, **no `question_text` persisted, no
assignment created** — never a stale/obsolete question silently assigned.

**Honest limitation, not a claimed guarantee**: no database transaction is
held open across the external Anthropic call (per this step's explicit
constraint), so this narrows the race window from "the entire LLM call
duration" down to "the final read-then-write" — it does not eliminate it. A
third observation arriving in the few milliseconds between the revalidation
read and the final commit is a real, accepted, un-closed race. **Verified
with a mocked simulation of exactly this race** (the gap-existence check
patched to return "present" on its first call and "resolved" on its second,
around a real/mocked LLM call in between): the attempt was correctly
discarded, `question_text` stayed `null`, and no assignment was created.

### Idempotency

`client_request_id` — the Step 12 analogue of
`client_submission_id`/`client_guide_id`/`client_audio_id`/
`client_location_id` (Step 5–7's established pattern), chosen over a
content-derived "generation key" because it's the codebase's dominant
existing convention for this exact problem shape, and unlike those columns,
there is no pre-existing entity (like a `Submission`) to key generation off
of in the first place — a "gap" is not itself a persisted row. Nullable: a
caller that omits it gets no idempotency (always generates fresh), matching
`client_location_id`'s optional behavior. A repeat call with the SAME
`client_request_id` and matching `knowledge_type`/coordinate returns the
existing question (replaying its current state, never re-calling the LLM
once `generated`); the same id with a DIFFERENT `knowledge_type`/coordinate
is rejected with `409` (mirrors `SubmissionConflictError`/
`LocationConflictError`'s `_ensure_compatible` pattern exactly).

This scopes deduplication to "retries/duplicates of the SAME logical
request" — not "any two independent requests for the same gap." Two
different callers generating for the same gap without sharing a
`client_request_id` will get two separate `Question` rows, exactly as two
different `client_submission_id`s for "the same" note already produce two
separate submissions elsewhere in this codebase — an accepted, pre-existing
behavior, not a new gap introduced here.

### Concurrency

Identical strategy to Transcription/Extraction: the `Question` row is locked
with `SELECT ... FOR UPDATE` only for the brief claim step — never held
across the LLM call. Row *creation itself* also needs the
IntegrityError-catch-and-refetch pattern (like `create_or_get_submission`),
because — unlike Extraction, whose lazy-creation race is against an
always-pre-existing `submission_id` — a genuine "two concurrent first-ever
triggers with the same `client_request_id`" race is possible here too.

**Verified with 3 real concurrent requests** (`curl ... &` / `wait`, sharing
one `client_request_id`, targeting a fresh `missing` gap): exactly one
reached Claude and became `generated` with one assignment; the other two
immediately returned `processing` with `question_text: null` and
`assignment: null`. Confirmed directly in PostgreSQL afterward: exactly one
`questions` row, `attempt_count: 1`, exactly one `question_assignments` row.

### No guide available

If, at generation time, no active guide's latest location is geographically
relevant to the gap (Step 11's `selected_guide` is `null`), the question is
still persisted as `generated` — **unassigned**, not discarded and not
assigned to a fabricated guide. It remains real, useful, queryable
knowledge-gap output; a future step can retry assignment as guides move or
new GPS data arrives (exactly the follow-up Step 11 itself anticipated).
Verified with a real generation at an isolated coordinate: `status:
'generated'` with a real `question_text`, `assignment: null`.

### Prompt design

`app/services/question_generation/prompt.py`'s system prompt explicitly
instructs Claude to: ask about only the supplied topic; never invent trail
conditions, weather, hazards, closures, or landmarks; treat any place name
given as background only, never proof of a condition; never invent a place
name when none is given; phrase a `missing` gap as "please check and report,"
a `stale` gap as "please send an update"; write naturally for someone
texting from the field; and — critically — never use internal words like
"knowledge type," "freshness window," "stale," "missing," "confidence
score," "database," or "LLM" in the question itself. Structured output is
forced via `tool_choice` (`generate_guide_question`), requiring
`question_text` (optional `short_context`) — deliberately **not** an
`urgency` field, even though Part F of this step's spec allowed one: Part G
is explicit that Step 11 remains the sole source of priority truth, so adding
a second, LLM-guessed notion of urgency would just create a competing,
unreliable signal. Instead, the real Step 11 provenance
(`safety_critical`/`default_priority`/`staleness_severity_hours`/`gap_rank`)
is snapshotted directly onto the `Question` row from the ranked gap itself,
never asked of the model.

**Verified against the real API**: a `missing` `snow_ice` gap (no nearest
place) produced *"Hey, can you check your current spot for any snow or ice on
the trail and let me know what you see?"* — no invented place, no internal
jargon. A `stale` `trail_condition` gap (~28h past its freshness window, no
nearest place) produced *"Hey, can you check the trail conditions where you
are right now and send an update? Last report we have is over a day old."* —
correctly update-oriented, referencing that a prior report exists, still no
invented place.

### What is stored where

**PostgreSQL, `questions` table**: the generated `question_text`/
`short_context`, `status`/`provider`/`model`/`error_message`/
`attempt_count`, and a SNAPSHOT of the gap's identifying + ranking context at
generation time — `knowledge_type_id`, `gap_state`, `target_latitude`/
`target_longitude`, `nearest_known_place_name`/`_distance_meters`,
`safety_critical`, `default_priority`, `staleness_severity_hours`,
`gap_rank`. Snapshotted (not live-joined) for the same reason Transcription/
Extraction snapshot their provider metadata: this row's historical meaning
must never silently change if `knowledge_type_config` or a nearby `Location`
is edited later.

**PostgreSQL, `question_assignments` table**: `question_id`, `guide_id`,
`status`, `assigned_at`, `answered_at` (always `null` in this step).

**Nothing new on the filesystem or in the mobile app's SQLite** — Step 12
reads only PostgreSQL data.

### Database schema decisions

**`Question` and `QuestionAssignment` as two separate tables**, not one —
deliberately, to support this step's explicit forward requirements: a
question may eventually be REASSIGNED (a new `QuestionAssignment` row for the
same `question_id`, a different `guide_id`), and assignment HISTORY may
matter later. `question_id` on `QuestionAssignment` is therefore **NOT
unique** — unlike Transcription/Extraction's one-row-per-submission pattern,
multiple assignment rows per question are a valid future shape. In THIS
step's actual code, at most one assignment is ever created per question (at
generation time, in the same transaction that marks the question
`generated`) — the schema simply isn't artificially constrained against the
future case.

**No `geog`/PostGIS column on `Question`**, unlike `Observation`/`Location`/
`GuideLocation` — deliberately: no query in this step needs to search
Questions spatially (there's no "questions near me" endpoint). The precedent
for a plain-Numeric coordinate pair with no `geog` already exists in this
codebase (`Submission.latitude`/`longitude`); add `geog` (and a GiST index)
exactly when a real query needs one, not before.

**No new index beyond `ix_questions_status` and
`ix_question_assignments_guide_id_status`** — the latter directly supports
`GET /guides/{guide_id}/questions`'s `WHERE guide_id = ? [AND status = ?]`
access pattern (mirrors `ix_transcriptions_status`/`ix_extractions_status`'s
precedent of adding exactly the index a new query needs, nothing
speculative).

**`aging_threshold_hours` is still not used** — same reasoning as Steps 10
and 11 (no defined semantics anywhere in this codebase for that field).

### Why the LLM provider is called only from the backend

The mobile app never holds `ANTHROPIC_API_KEY` — same guarantee as Step 9,
unchanged: not in mobile source, `app.json`, any `EXPO_PUBLIC_*` variable, or
`mobile/.env`. The mobile app only ever calls this backend's own
`GET /api/v1/guides/{id}/questions` — it never generates a question itself,
and never talks to Anthropic directly.

## Guide answer workflow (Step 13)

Closes the loop opened by Step 12: a guide answers their assigned question,
the answer is durably persisted, the assignment becomes `completed`, and the
answer becomes available to the EXISTING extraction pipeline (Step 9,
completely unmodified) as a new source of knowledge — no second LLM path, no
new provider integration.

```
POST /api/v1/questions/{question_id}/answers
GET  /api/v1/questions/{question_id}/answers/{answer_id}
```

### Submit an answer

```
curl -X POST http://127.0.0.1:8000/api/v1/questions/<question_id>/answers \
  -H "Content-Type: application/json" \
  -d '{
    "guide_id": "<guide_id>",
    "client_answer_id": "b1e7c2a0-3f4d-4e5a-9c1b-8d2f6a7e0c11",
    "answer_text": "There is about 15cm of fresh snow near the ridge, icy in the shaded sections. Passable with microspikes.",
    "answered_at": "2026-08-26T13:00:00Z"
  }'
```

Returns the full `QuestionRead` (its `assignment.status` is now `completed`
and `answer` is populated) — `201` on first success, `200` on an exact
idempotent replay:

- `404` — question doesn't exist.
- `400` — question has no current assignment (Step 12's "no guide available"
  case — nobody to answer against), or its assignment was `cancelled`.
- `403` — this question is currently assigned to a **different** guide.
- `409` — the assignment is already `completed` (a genuinely new
  `client_answer_id` arriving after the fact — one guide answer must never
  silently overwrite another), OR `client_answer_id` was reused with
  different answer data.
- `422` — `answer_text` blank/whitespace-only, or `client_answer_id` not a
  valid UUID string.

### Architecture

```
POST /api/v1/questions/{id}/answers {guide_id, client_answer_id, answer_text, answered_at?}
    |
    v
app/services/question_answers.py  (lock the CURRENT assignment, verify
    |                               ownership/status, persist)
    |
    |  builds a Submission with:
    |    submission_type = 'answer'
    |    latitude/longitude = the QUESTION's own target coordinates (Part F)
    |    source_question_id = this question  (NEW provenance column)
    v
app/db/models/submission.py  (unmodified table, one new nullable FK column)
    |
    |  QuestionAnswer row created, referencing the Submission
    |  QuestionAssignment.status = 'completed', .answered_at = answered_at
    v
PostgreSQL, ONE commit (answer + submission + assignment update all atomic)
    |
    |  ... later, an OPERATOR/CALLER explicitly triggers, exactly like any
    |      other submission (no automatic chaining — see "Deliberately NOT
    |      implemented" below):
    v
POST /api/v1/submissions/{submission_id}/extract
    |
    v
app/services/extractions.py  (COMPLETELY UNMODIFIED — same claim/lock,
    |                          same Anthropic call, same validation)
    v
app/services/source_text.py  ('answer' submissions resolve their source text
                               via raw_text, the SAME branch as 'note' — a
                               one-line tuple change, not a new code path)
```

No new LLM call, no new provider file, no new prompt, no new validation
module, no duplicated knowledge-type checking, no duplicated observation
persistence, no duplicated geographic-context resolution — every one of
those is the exact Step 9 code, called with a `submission_id` like any other.
**Verified against the real API**: answering a `snow_ice` question with the
text above and then calling `POST .../extract` on the resulting submission
produced two real, correctly-typed observations —
`snow_ice: {"depth_cm": 15, "condition": "fresh snow with icy patches", ...}`
and `trail_condition: {"condition": "passable", "requirement": "microspikes"}`
— proving the extraction pipeline was reused entirely unmodified rather than
narrowly hard-coded to the question's own knowledge type.

### Assignment state transitions

Reuses the **existing** `QuestionAssignment` state machine from Step 12
(`app/db/models/question_assignment.py`) — no new/competing state machine:

- `assigned` → unchanged from Step 12: the question is waiting for the guide.
- `active` → **deliberately still not set by any code**. Step 12 defined it
  for "the guide has started answering," but this project's mobile
  architecture is offline-first with no separate "I opened this question"
  network event — inventing one would mean either a network call the compose
  screen doesn't actually need (violating Part G's "must not depend on an
  immediate network response"), or a purely-local flag with no server
  meaning, which is exactly the kind of second, competing state machine this
  step's spec says not to invent. Left reserved, same as `cancelled`.
- `completed` → set **only** inside `submit_answer`, in the same transaction
  that persists the `QuestionAnswer` and its backing `Submission` — never
  because text merely exists on the mobile device. This is the one
  authoritative, backend-only transition this step adds.
- `cancelled` → unchanged from Step 12: still no code sets it; answering a
  `cancelled` assignment is explicitly rejected (`400`) rather than silently
  allowed. **Verified** by manually setting an assignment to `cancelled` and
  confirming the answer endpoint refuses it.

### Idempotency & concurrency

`client_answer_id` — the Step 13 analogue of `client_request_id`/
`client_submission_id`/etc. **Required** (unlike some of those), because an
answer with no idempotency key at all would let a flaky connection silently
create two competing answers for one assignment. A repeat call with the SAME
id and matching payload replays the existing answer (`200`, no duplicate); the
same id with different data is a `409` (`_ensure_compatible`, same pattern as
`SubmissionConflictError`/`QuestionConflictError`).

Concurrency reuses the "serialize on the thing being mutated" pattern from
`attach_audio_to_submission`: the assignment row is locked
(`SELECT ... FOR UPDATE`) for this function's entire duration (there is no
external/LLM call to avoid holding it across, unlike question generation) —
only the first concurrent caller to acquire the lock can transition
`assigned`/`active` → `completed`; every other concurrent caller observes
`completed` already set. **Verified with 3 real concurrent requests**
(distinct `client_answer_id`s, same question): exactly one returned `201`,
the other two immediately returned `409` ("already answered"). Confirmed in
PostgreSQL: exactly one `question_answers` row, one `submissions` row.
**Also verified**: exact idempotent replay of the winning `client_answer_id`
→ `200`, identical `submission_id`, still exactly one row of each.

### Geographic & temporal correctness (Part F)

The answer's `Submission.latitude`/`longitude` are set to the **Question's
own snapshotted `target_latitude`/`target_longitude`** — the location the
underlying knowledge gap actually concerns — never the guide's live GPS
position at answer time. This is a structural choice, not a runtime check:
`submit_answer` never reads `GuideLocation` at all. A guide typing an answer
hours later, from a different spot (or fully offline, no GPS fix available)
still produces a correctly-geolocated observation once extracted, because
`extractions.py`'s existing `_resolve_observation_coordinates` picks up
`submission.latitude`/`longitude` directly (its "submission already has
coordinates" branch — unmodified). `submitted_at`/`observed_at` are the
guide's own `answered_at` (device-local answer time), not server-receipt
time — the same `submitted_at`-vs-`created_at` distinction already used by
every other `Submission`.

### What is stored where

**PostgreSQL, `question_answers` table**: `question_id`, `assignment_id`,
`guide_id`, `client_answer_id`, `answer_text`, `submission_id`,
`answered_at`. A dedicated table, not columns on `Question` (whose whole
purpose is Step 12's LLM generation lifecycle) or `QuestionAssignment`
(whose purpose is the assignment lifecycle) — "what did the guide actually
say" is a third, genuinely different concern.

**PostgreSQL, `submissions` table**: one new nullable column,
`source_question_id` (FK → `questions.id`, `ON DELETE SET NULL`, indexed) —
the only schema change to an existing table. Traces `Submission` → `Question`
provenance; `QuestionAnswer.submission_id` is the complementary
`Question`/`Answer` → `Submission` direction. Together with the unmodified
`Extraction`/`Observation` tables, the full provenance chain
`Observation → Submission → Question → QuestionAssignment → Guide` is
traceable with plain joins — **verified directly in PostgreSQL** after a
real extraction: both resulting observations' `submission_id` led back to a
submission whose `source_question_id` matched the original question.

**Nothing new in the mobile app's SQLite beyond the new `local_answer`
table** (see `mobile/README.md`) — the answer text itself lives there until
synced; nothing about extraction/observations ever reaches the mobile app.

### Database schema decisions

**`QuestionAnswer` as its own table**, not answer columns bolted onto
`Question` or `QuestionAssignment` — same reasoning Steps 8/9/12 already
established for keeping genuinely different lifecycles in separate tables.

**Representing the answer as a `Submission`** (`submission_type = 'answer'`)
rather than inventing a parallel "answer extraction" system — the explicit,
required design choice for Part E. `source_text.py`'s note-vs-voice branch
became a `("note", "answer")` tuple check (one line) instead of a new
branch, since an answer's text lives directly in `raw_text` exactly like a
note's. No `SUPPORTED_CAPTURE_TYPES`/`SubmissionCreate.capture_type` change
was needed — that `Literal["note", "voice"]` schema still only governs the
**direct** `POST /api/v1/submissions` endpoint; `'answer'` submissions are
only ever created internally by `question_answers.py`, never through that
endpoint, so the client-facing contract there is intentionally untouched.

**`client_answer_id` doubles as the created `Submission`'s
`client_submission_id`** rather than minting a second server-side id — unlike
a note and its separately-uploaded audio (two distinct client actions), an
answer and "the submission it produces" are the SAME guide action from the
client's perspective; reusing the id also lets the existing
IntegrityError-catch-and-refetch race pattern double as this function's own
idempotent-replay recovery path.

**No new index needed beyond `ix_question_answers_question_id` and
`ix_submissions_source_question_id`** — both directly support the provenance
read patterns above (`GET .../answers/{id}` and any future
"submissions produced by this question" query); nothing speculative added.

### Why the LLM provider is called only from the backend

Unchanged from Step 12: this step adds **no new LLM call at all**. Answering
a question never touches Anthropic — only a subsequent, separate, explicit
`POST .../extract` (unchanged since Step 9) does, and that already only ever
runs on the backend. `ANTHROPIC_API_KEY` remains backend-only.

## Knowledge aging: the 'aging' state (Step 14)

Adds a fourth knowledge state -- `aging` -- between `fresh` and `stale`,
using `KnowledgeTypeConfig.aging_threshold_hours` (a column that existed
since the original schema but was **never used anywhere in this codebase
until now** -- verified by inspection: no reference in `knowledge_state.py`,
`knowledge_decisions.py`, or any migration/README/test before this step).
No new endpoints, no schema/migration changes at all (`alembic check`
confirms "No new upgrade operations detected" both before and after) --
this step is pure evaluation-logic + response-shape evolution on the
**existing** Step 10/11/12 services.

### Exact aging semantics

Given `freshness_expires_at = observed_at + freshness_window_hours` and,
when `aging_threshold_hours` is configured (including the value `0`),
`aging_expires_at = freshness_expires_at + aging_threshold_hours`:

```
evaluation_time <= freshness_expires_at                        -> fresh
freshness_expires_at < evaluation_time <= aging_expires_at      -> aging
evaluation_time > aging_expires_at                              -> stale
```

`aging_expires_at` is `null` only when `aging_threshold_hours` itself is
`null` (no aging period configured at all) -- in that case the classification
above simply skips the middle branch: `fresh` transitions **directly** to
`stale` the instant `evaluation_time` passes `freshness_expires_at`,
identical to pre-Step-14 behavior. `aging_threshold_hours = 0` produces the
SAME observable transition (`fresh` → `stale` directly) without any special
case in the code: `aging_expires_at` still gets a real (zero-width) value
equal to `freshness_expires_at`, so the `aging` branch's own upper-bound
check can never be satisfied for an instant not already claimed by the
`fresh` check above it. **Verified against real PostgreSQL data for both
`aging_threshold_hours = NULL` and `= 0`** -- both went `fresh` at
exactly the freshness boundary, `stale` one second later, with no `aging`
state in between.

**Boundary rules (all verified against real data, using the spec's own
worked example: `freshness_window_hours=6`, `aging_threshold_hours=2`,
`observed_at=10:00`)**:

| evaluation_time | state | severity_hours |
|---|---|---|
| 10:00 (at observed_at) | fresh | 0.0 |
| 16:00:00 (exactly `freshness_expires_at`) | fresh | 0.0 |
| 16:00:01 | aging | ~0.0 |
| 18:00:00 (exactly `aging_expires_at`) | aging | 2.0 |
| 18:00:01 | stale | ~0.0 |

### Severity

A new, generalized `severity_hours` field on `KnowledgeTypeState`
(`app/services/knowledge_state.py`) — always `>= 0` (clamped defensively,
though the boundary rules already guarantee non-negativity by
construction):

- `missing` / `fresh` → `0.0`
- `aging` → `evaluation_time - freshness_expires_at`
- `stale` → `evaluation_time - aging_expires_at` when an aging period is
  configured, else `evaluation_time - freshness_expires_at`

`RankedGap.staleness_severity_hours` (Step 11) is **kept under its existing
field name** for backward compatibility with already-persisted
`Question.staleness_severity_hours` provenance, but is now simply this
value carried through from Step 10 rather than independently recomputed
(Step 11 previously re-derived it from `freshness_expires_at` alone, before
`aging` existed) — one authoritative computation, not two.

### Gap semantics and ranking

`fresh` is the only non-gap state; `gap_count = aging_count + stale_count +
missing_count` (`KnowledgeStateSummary` gained `aging_count`). Ranking
precedence (`app/services/knowledge_decisions.py::_gap_sort_key`) is now:

1. `safety_critical` first (unchanged).
2. Gap state urgency: `missing` > `stale` > `aging` (new, via a single
   centralized `_GAP_STATE_URGENCY_RANK` mapping — Part D's explicit
   requirement).
3. `default_priority` (unchanged direction/logic).
4. Severity within the same state (unchanged formula, now sourced from
   `severity_hours`).
5. `knowledge_type` name, ascending (unchanged tie-break).

Still an explainable, ordered tuple — never a blended score.
**Verified against real PostgreSQL data**: a safety-critical `aging` gap
outranked a non-critical `stale` gap (criterion 1 dominates criterion 2); a
non-critical `stale` gap outranked a non-critical `aging` gap at equal
severity (criterion 2 dominates criterion 4); `missing` outranked `stale`
outranked `aging` among otherwise-equal non-critical gaps; higher
`default_priority` ranked first at equal state/safety; two repeated calls
produced byte-identical ordering (tie-break stability).

### Question generation

`app/services/question_generation/prompt.py`'s `build_user_message` now
branches on three situations instead of two — `missing` ("check and
report"), `aging` (a new, deliberately low-pressure "recent-ish report
exists, not yet out of date — send a quick confirmation" framing), `stale`
(unchanged "send an updated report"). The system prompt's jargon blocklist
gained `"aging"`/`"grace period"`. No new Anthropic provider, no new tool
schema — the exact same `generate_question_text`/`validate_question_output`
path Step 12 already established. **Verified against the real API**: an
`aging` `trail_condition` gap produced *"Hey, whenever you get a sec, could
you shoot me a quick update on the trail conditions at your current
location? Just want a fresh check-in."* — correctly low-pressure, no false
claim of missing information, no internal jargon. `missing` and `stale`
generation re-verified unchanged. A `fresh` knowledge type still correctly
returns `400` (`GapNotFoundError`) with **no LLM call made at all** (the
gap-existence check runs before any provider call, unchanged from Step 12).

`Question.gap_state` is an immutable, point-in-time **snapshot** — a
question generated while a gap was `aging` keeps reading `'aging'` forever,
even after live knowledge state later reclassifies the same gap as `fresh`
or `stale`. Nothing in this step recomputes an existing Question's
snapshot. Verified directly: after answering and extracting a real
observation that made the underlying gap `fresh` again, the original
Question row's `gap_state` still read `'aging'`.

### Full lifecycle, verified end-to-end with real data

1. Inserted a real, historically-dated `trail_condition` observation → the
   type genuinely evaluated as `aging` at a chosen `evaluation_time`
   (confirmed via `GET /api/v1/knowledge-state`).
2. Generated a real question for that `aging` gap (`gap_state: "aging"`
   snapshotted).
3. Submitted a real answer as the assigned guide (assignment →
   `completed`).
4. Called the **existing**, explicit `POST .../extract` (never
   auto-triggered — unchanged from Step 13) → two real observations
   persisted, correctly typed, geolocated at the question's own target
   coordinate, evidenced from the actual answer text.
5. Re-evaluated `GET /api/v1/knowledge-state` at the current real time (no
   `evaluation_time` override) → `trail_condition` now reads `fresh`,
   because the newly-extracted observation is the same knowledge type,
   within the same geographic radius, and recently observed — genuinely
   relevant on all three axes, not a fabricated improvement.

### What is stored where / schema

No schema changes. `aging_threshold_hours` was already a nullable `Integer`
column on `knowledge_type_config` (present since the original migration,
unused until now). `KnowledgeTypeState.aging_expires_at`/`severity_hours`
and `KnowledgeStateSummary.aging_count` are new **Pydantic response
fields only** — nothing new persisted to PostgreSQL. `pg_indexes` inspected
before starting: `ix_observations_knowledge_type_id_observed_at` and
`idx_observations_geog` already fully support the (unchanged) observation
lookup query; aging classification is pure Python arithmetic on the
already-fetched row, so no new index was needed or added.

## Explore & a growing knowledge system (Step 16)

Step 16 adds a second way knowledge enters the system, and — more
significantly — lets the set of knowledge *categories* itself grow.

### Two collection modes, deliberately separate

| | **Questions** (Steps 12–13) | **Explore** (Step 16) |
|---|---|---|
| Purpose | Collect knowledge we already know is missing | Discover knowledge before we know we need it |
| Trigger | System-generated from a ranked gap | Guide opens the Explore tab |
| Persisted? | Yes — `Question` + `QuestionAssignment` | No — prompts are built on the device |
| Becomes | `Submission(submission_type='answer')` | `Submission(submission_type='explore')` |
| Assigned? | Yes, to one guide | No — always available |

Both converge on the SAME pipeline: a `Submission` with `raw_text`, extracted
by the existing `POST /api/v1/submissions/{id}/extract` into `Observation`
rows. Explore required **no second extraction system** — adding `'explore'` to
one tuple in `app/services/source_text.py` was enough.

Explore prompts are generated **client-side** from context the backend already
exposes (`/guides/{id}/context`, `/guides/{id}/knowledge-state`). No new
endpoint, no prompt table, no prompt lifecycle, no LLM call. See
`mobile/src/explore/explorePrompts.ts` for the full rationale.

### The full product loop

```
Explore contribution  ->  extraction  ->  existing type?  -> Observation
                                       \
                                        -> new reusable  -> KnowledgeTypeConfig
                                           category         + Observation
                                                                  |
       fresh -> aging -> stale -> ranked gap -> Question ---------+
                                                    |
                                              Questions tab
                                                    |
                                              guide answers
                                                    |
                                          Submission -> extraction
                                                    |
                                            fresh knowledge again
```

### Case A / B / C — when a new knowledge type is created

Extraction now returns two arrays: `observations` (against existing types) and
`new_knowledge_types` (proposed categories).

- **Case A — fits an existing type.** Normal `Observation` against it. If the
  model proposes a "new" category whose *normalized* name matches an existing
  active type (e.g. `Trail-Condition` → `trail_condition`), the observation is
  silently recorded against that existing type rather than rejecting the
  extraction.
- **Case B — a genuinely new, reusable category.** A `KnowledgeTypeConfig` row
  is created (`active=True`, so it immediately joins the lifecycle) plus its
  `Observation`.
- **Case C — random/personal/non-reusable.** Nothing is created. `"I drank tea
  at 4 PM"` produces zero observations and zero types (verified).

**The criterion**, enforced in the system prompt: it must be a reusable
*category* (not a one-off fact), about the *place or its conditions*, that the
system could sensibly ask a different guide about again in future.

### The LLM is never the database authority

This is the load-bearing safety property. The model may only **select one value
from each of three fixed, application-owned enumerations**. It can never supply
a number, a boolean, or any policy value:

| Model chooses | Application decides (`app/services/knowledge_type_policy.py`) |
|---|---|
| `volatility`: `hours` / `days` / `weeks` / `months` | `freshness_window_hours`, `aging_threshold_hours` |
| `scope`: `point` / `local` / `area` | `geographic_relevance_radius_meters` |
| `significance`: `safety` / `practical` / `enrichment` | `safety_critical`, `default_priority` |

Profile values are anchored to the four hand-seeded types, so a dynamic type
lands in the same value space as a hand-tuned one:

```
hours  -> 6h / 3h     (anchored on weather)        point -> 500m    (obstruction)
days   -> 72h / 24h   (anchored on trail_condition) local -> 2000m  (trail_condition)
weeks  -> 336h / 168h                               area  -> 10000m (weather)
months -> 2160h / 720h
safety -> safety_critical=True,  priority 5   practical -> False, 3   enrichment -> False, 1
```

Additional deterministic guards, all in application code:

- **Name normalization** — `"Parking Availability"`, `"parking-availability"`,
  and `"parking  availability"` all collapse to `parking_availability`, which
  is what makes duplicate detection real.
- **Reserved names** — the four seeded types can never be redefined.
- **Hard cap** — at most `MAX_NEW_TYPES_PER_EXTRACTION` (2) new types per
  extraction.
- **Unknown enum value → reject the whole extraction.** Never a fallback guess.
- **All-or-nothing** — one malformed proposal rejects the entire extraction
  rather than persisting the observations that happened to be fine.
- **Intra-response dedup** — two proposals normalizing to the same name are
  collapsed, never inserted twice.

**Honest limitation:** the application validates *structure*, not *semantics*.
It cannot itself judge whether a category is genuinely reusable — that judgement
lives in the prompt. The cap and the reserved list bound the blast radius if the
model misjudges; they do not eliminate it. Auditing
`knowledge_type_config` occasionally is expected.

### Concurrency & idempotency

`create_or_get_dynamic_type` uses **IntegrityError-catch-and-refetch**, not
`SELECT ... FOR UPDATE` — this is an INSERT race, and you cannot lock a row that
does not exist yet. The DB unique constraint on `knowledge_type` is the real
guarantee. *Verified with 8 genuinely concurrent threads: exactly one
`created=True`, all 8 returned the same id, exactly one row.*

Type creation happens **inside the same transaction** as the observation inserts
and the `completed` flip, so a crash can never leave a new type with no
observation, or observations under an incomplete extraction.

### `active` semantics

An existing type is reused whether active or not, and an inactive one is
**never reactivated** — `active` is a human decision an LLM proposal must not
undo. The observation is still recorded (never discarded); it simply does not
participate in knowledge-state evaluation until an administrator reactivates
the type.

### Photos

`POST /api/v1/submissions/{id}/photo`, restricted to `explore` submissions.
Mirrors the audio attachment exactly: idempotent on `client_photo_id` (a third
distinct client id), row-locked, server-generated storage key, client filename
never used as any part of a path.

Validation (`app/services/photo_validation.py`) adds a **magic-byte check** on
top of the content-type/extension allow-list — image formats have short,
reliable signatures, so a text file renamed `.jpg` is rejected. (Audio has no
equivalently simple story, which is why Step 7 documented that check as
deferred rather than faking one.)

**A photo never becomes an observation.** This step does no image
understanding. An Explore contribution always carries the guide's own text, and
that text is what extraction reads. The photo is durable evidence attached to
the same submission — the mobile copy says so plainly rather than implying the
image is analysed.

Storage was generalized (`MediaStorage` / `LocalFilesystemMediaStorage`) with
`AudioStorage`/`StoredAudio`/`LocalFilesystemAudioStorage` kept as aliases, so
no existing call site changed. Photos use a separate configured directory
(`photo_storage_dir`) so the two can be given different operational treatment.

### Migration

`386c20775143` adds the five `photo_*` columns plus
`uq_submissions_client_photo_id`. Purely additive and fully nullable — **no
backfill**, because a pre-Step-16 submission genuinely has no photo (NULL is
the truthful value, not a placeholder). The unique constraint is named
explicitly rather than left to autogenerate's `None`, which would have produced
an undroppable constraint and a broken `downgrade()`. Upgrade → downgrade →
upgrade round-trip verified against real PostgreSQL.

### Deliberately NOT implemented in Step 16

Automatic/background extraction (still the explicit `POST .../extract`),
prompt persistence, LLM-generated prompts, image understanding/vision,
knowledge-type merging or retirement tooling, an admin UI for reviewing
dynamically created types, reassignment, notifications, embeddings, vector
search, RAG, or any background worker/queue.

## Explore voice notes & the guide profile (Step 17)

Two mobile features — a voice note on an Explore contribution, and an editable
guide profile — reached the backend. Both were deliberately small changes.

### No migration was needed

`Submission` has carried `audio_*` columns since Step 7 and `photo_*` columns
since Step 16, and they were already **independent of one another** (the model
even noted that nothing structurally prevented a submission from having both).
So an Explore contribution carrying text, a photo and a voice note needed **no
new column, no new table, and no new storage path** — only permission to do what
the schema already allowed.

Likewise `Guide` already had `name` and `phone_number`, so the profile endpoint
needed no migration either.

**`alembic check` is clean — Step 17 added no revisions.**

### What actually changed

Four edits, all narrow:

1. **`schemas/submission.py`** — added `AUDIO_CAPABLE_SUBMISSION_TYPES =
   ("voice", "explore")` as the single shared allow-list, and made
   `text_content` optional for `'explore'`.
2. **`api/routes/submissions.py`** — the audio upload route now accepts any
   submission in that allow-list instead of only `'voice'`.
3. **`services/transcriptions.py`** — the same allow-list gates
   `start_transcription`. `SubmissionNotVoiceError` was renamed
   `SubmissionNotAudioCapableError` (the old name is kept as an alias), because
   "not voice" had stopped being the real reason a request is refused.
4. **`services/source_text.py`** — `'explore'` resolves its source text from
   `raw_text` when the guide typed something, and otherwise falls through to the
   **same** transcription branch `'voice'` uses.

The allow-list is defined once and imported by both the upload route and the
transcription service specifically so the two can never drift into the state
"audio accepted, but transcription refused" — which would be a silent dead end
for the guide rather than a visible error.

### Source text resolution for 'explore'

```
explore submission
  ├─ raw_text is non-blank        -> use it (unchanged from Step 16)
  ├─ raw_text blank, audio present -> resolve via Transcription, exactly as 'voice':
  │     no Transcription row  -> TranscriptionMissingError
  │     pending / processing  -> TranscriptionNotReadyError
  │     failed               -> TranscriptionFailedError
  │     completed but blank  -> EmptyTranscriptError
  │     completed            -> the transcript
  └─ neither text nor audio  -> EmptySourceTextError
```

Every "not ready" reason keeps its own pre-existing error type rather than
collapsing into a generic failure, so the mobile app can keep reporting exactly
what is happening.

Text wins over a transcript when both exist: it is what the guide actually
typed, needs no provider call, and is available immediately.

### Why 'explore' may now be created without text

An Explore submission with no `text_content` is accepted, because audio is
attached by a **separate later request** — the server genuinely cannot know at
creation time whether a voice note is coming. This is precisely the same
ordering that has always applied to `'voice'` submissions.

The consequence is stated plainly rather than hidden: an `'explore'` submission
that never receives audio and has no text simply has nothing to extract, which
`resolve_source_text` reports as `EmptySourceTextError`. The mobile app enforces
"text or voice" before saving; that is a **client-side product rule, not a
server guarantee**, and it is documented as such.

`'note'` still requires text, and `'voice'` still refuses it. Neither changed.

### `PATCH /api/v1/guides/{guide_id}` (new)

Partial update of a guide's editable identity fields.

```
PATCH /api/v1/guides/{guide_id}
{ "name": "Tenzin", "phone_number": "+91 98765 43210" }
```

- Accepts **only** `name` and `phone_number`. Both optional; a body setting
  neither is rejected with 422.
- `"phone_number": null` **clears** the number. Omitting the key leaves it
  untouched — `model_fields_set` distinguishes "not mentioned" from "set to
  null", so a name-only update can never blank a phone number.
- Never touches `client_guide_id`. That is the stable identity the guide is
  resolved by, and rewriting it would orphan every local record on the device.
- 404 if the guide does not exist.
- Naturally **idempotent**: it sets absolute values rather than applying a
  delta, so re-running it after a lost response converges on the same state.
  That is why, unlike submission/answer creation, it needs no client-generated
  id.

**No row lock, deliberately.** This writes two independent scalar columns with
no read-then-write step a concurrent update could interleave with, so it is
safe last-write-wins. (Contrast `attach_*_to_submission`, which *does* lock,
because it decides what to write based on what it just read.)

### The privacy boundary: profile metadata is not knowledge

The mobile Profile screen also holds an "About you" note and a profile photo.
**Neither exists on the backend at all** — no column, no endpoint, no request
carries them. That is enforced by construction, not by convention:

- `GuideUpdate` has exactly two fields.
- There is no guide-avatar upload route.
- Profile data never enters extraction, transcription, observations,
  embeddings, or any LLM prompt. The extraction pipeline reads submission text
  and transcripts; it has no access path to guide profile fields.

Name and phone are stored because they are operational identity — who filed a
report and how to reach them — not because they are field knowledge. They never
become Observations, never affect knowledge freshness, and never generate
Questions.

## Admin dashboard — content curation & moderation layer (Step 18)

A new admin web app ([`admin/`](../admin/README.md)) sits between field
collection and any future public-facing app. Its rule is simple and absolute:
**nothing an AI extracts or a guide submits becomes publicly visible just
because it exists.** A human decides. This step adds exactly the backend
surface that rule requires — no second database, no parallel knowledge
system, no change to any existing mobile-facing endpoint or workflow.

### The moderation model

A **sixth independent state machine**, alongside `sync_status` (mobile-local),
`Transcription.status`, `Extraction.status`, `Question.status`, and
`QuestionAssignment.status`. It answers a question none of those do: "has a
human approved this piece of knowledge for eventual public visibility?"

`observation_moderation` is a **new table**, one row per `Observation`
(enforced by a `UNIQUE` foreign key) — deliberately *not* status columns
added to `Observation` itself. Every other lifecycle in this codebase
(Transcription, Extraction, Question, QuestionAssignment) already follows
this same "new lifecycle = new table" convention; moderation is no
exception. Values: `pending_review` (the default — set atomically the moment
an `Observation` is inserted, inside the same transaction as the insert, in
`services/extractions.py`), `approved`, `rejected`.

Because one submission can produce several observations (e.g. one voice note
→ `snow_ice` + `trail_condition`), moderation is scoped to the **observation**,
not the submission — each is reviewed and decided independently, while the
originating `Submission` (raw text/audio/photo) is read-only evidence, never
duplicated or rewritten by a decision.

**Approve/reject only ever act on a `pending_review` observation.** Switching
an *already-decided* observation to the opposite decision is a deliberately
separate action — `POST .../change-decision` — never something the same
approve/reject buttons do silently. All three endpoints lock the moderation
row (`SELECT ... FOR UPDATE`) for the duration of the decision, the same
pattern used throughout this codebase (e.g. `attach_audio_to_submission`), so
two concurrent decisions on the same observation are fully serialized rather
than racing.

Rejection records one of a small closed set of reasons — `inaccurate`,
`unsafe`, `duplicate`, `poor_quality`, `not_useful`, `other` — plus an
optional free-text note. Rejecting (or re-rejecting) never deletes or alters
the source `Submission`/`Observation`.

### Database changes

One new table, `observation_moderation`, added by migration `13e123a398eb`
(revises `386c20775143`). Purely additive — no existing table or column is
touched. The migration also backfills a `pending_review` row for every
`Observation` that existed before this step, so "every Observation has a
moderation row" holds for old data too. Verified with `alembic check` (no
drift) against a live database.

### Authentication (development-safe, not production-grade)

Nothing resembling authentication existed anywhere in this backend before
this step — confirmed by inspection, not assumed. Every `/api/v1/admin/*`
route is now gated by a single shared secret:

```
ADMIN_API_TOKEN=<a long random string>
```

set as a backend environment variable. Requests must send it as the
`X-Admin-Token` header (an optional `X-Admin-Name` header supplies a
self-reported display label, used only for `decided_by` attribution — **not**
a verified identity). `ADMIN_API_TOKEN` unset means the admin API is
unreachable (503), not open. See `app/core/admin_auth.py`. This is explicitly
a placeholder for real per-admin accounts, stated as such rather than implied
otherwise — do not expose this deployment beyond a small trusted team as-is.

### CORS

The mobile app was never subject to CORS (React Native's `fetch` isn't a
browser). The admin web app is, so `CORSMiddleware` is now registered in
`app/main.py`, scoped to an explicit allow-list:

```
ADMIN_CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

Deliberately never `*` — the admin API returns contributor phone numbers.

### Endpoints

All under `/api/v1/admin/`, all requiring the admin token:

```
POST /auth/verify                          Checks a token; used by the admin login screen
GET  /overview                              Real, live counts — never fabricated
GET  /review-queue                          Defaults to status=pending_review
GET  /knowledge                             Same shape, all statuses by default
GET  /reviews/{observation_id}              Full provenance: source, extraction,
GET  /knowledge/{observation_id}            live knowledge context, related + sibling observations
POST /reviews/{observation_id}/approve      Only from pending_review
POST /reviews/{observation_id}/reject       Only from pending_review; body: {reason, note?}
POST /reviews/{observation_id}/change-decision   Only from an already-decided state;
                                             body: {status, reason?, note?}
GET  /places                                 Reuses `locations` + PostGIS ST_DWithin — no Haversine
GET  /places/{location_id}
GET  /contributors                           Aggregated per Guide; phone_number never in the list view
GET  /contributors/{guide_id}                 phone_number appears here only
GET  /questions                              Read-only visibility into Question/QuestionAssignment —
                                             does NOT touch or redesign that workflow (Step 12/13)
GET  /submissions/{submission_id}/audio      Evidence playback, via MediaStorage.read_bytes()

```

Example flow:

```
curl -X POST http://127.0.0.1:8000/api/v1/admin/reviews/<observation_id>/approve \
  -H "X-Admin-Token: $ADMIN_API_TOKEN" -H "X-Admin-Name: Nishka"

curl -X POST http://127.0.0.1:8000/api/v1/admin/reviews/<observation_id>/change-decision \
  -H "X-Admin-Token: $ADMIN_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"status": "rejected", "reason": "unsafe", "note": "conditions have since changed"}'
```

### No conflict/duplicate detection exists — and none is faked

Confirmed by inspection: nothing in this codebase detects conflicting or
duplicate observations. Rather than pretending otherwise, Review Detail's
`related_observations` is a real, working query — other observations of the
*same knowledge type*, within that type's own configured
`geographic_relevance_radius_meters`, ordered by distance (or recency if the
observation has no coordinate) — that a human reads and judges themselves.
The backend never claims to have detected a conflict.

### The future public-content boundary

No public-facing endpoint is built in this step. The boundary is
established structurally: "publicly approved content" is always exactly
`observations JOIN observation_moderation WHERE status = 'approved'` — the
identical join `GET /admin/knowledge` already exercises. A future public API
would reuse this same join with internal-only fields (`decided_by`, raw
contributor identity, etc.) simply omitted from its response schema.

### Known gaps

- No real per-admin identity/session — see "Authentication" above.
- `change-decision` does not keep a full audit trail of prior decisions,
  only the current one (`decided_by`/`decided_at`/`rejection_reason` are
  overwritten, not appended-to). Acceptable for this step; a `moderation_history`
  table would be the natural extension if that's ever needed.
- Review Detail's "related observations" panel scopes by the SAME knowledge
  type only — it does not attempt to find conceptually-related observations
  of a *different* type (e.g. `snow_ice` vs. `trail_condition` at the same
  spot). That is a genuinely different, harder problem, not attempted here.
- `admin/submissions/{id}/audio` and `/photo` stream the whole file in one
  response (no HTTP range/partial-content support) — fine for a short voice
  note or a phone photo, not built for large media.

## Automatic extraction triggering (Step 19)

Every step through Step 18 deliberately made extraction (and transcription)
**explicit-only**: a human/UI action had to call `POST .../extract` for
anything to happen — "no polling, no auto-trigger, backend truth over UI
guesswork" (see `mobile/src/screens/PendingItemsScreen.tsx`). Step 19
reverses that specific decision, by product request: extraction now runs
**automatically**, the moment a submission's source text first becomes
available, with no explicit trigger required.

### Where it hooks in

`app/services/extractions.py::maybe_trigger_extraction(db, submission_id)` is
the one place this policy lives — it resolves the submission's source text
(reusing `source_text.py` unchanged) and, if text is actually available,
calls the existing `start_extraction` unchanged. If text isn't available yet
(e.g. a voice-only submission whose transcription hasn't completed), it's a
silent, harmless no-op — nothing failed, it just isn't time yet. It is called
from exactly three places, matching the three ways source text can newly
become available:

- `services/submissions.py::create_or_get_submission` — right after creating
  a **new** `'note'` submission, or an `'explore'` submission that already
  carries text. (Never called on an idempotent replay of an
  already-existing submission — that would just re-check a state that was
  already triggered once.)
- `services/question_answers.py::submit_answer` — right after creating the
  `Submission` that represents a guide's answer (its text is available
  immediately, exactly like a note).
- `services/transcriptions.py::start_transcription` — right after a
  `'voice'` or voice-bearing `'explore'` submission's transcription
  **freshly** completes (not on an already-completed early return, which
  would have already triggered this the first time it completed).

### Why this is safe

`maybe_trigger_extraction` **never raises** — the action that triggered it
(submission creation, answer submission, transcription completion) must
always succeed regardless of whether extraction itself can run right now.
Every failure mode is swallowed and logged rather than propagated: no source
text yet, no `ANTHROPIC_API_KEY` configured, a transient provider error, or
any other unexpected exception. This required one deferred (function-local,
not module-level) import in `transcriptions.py`, to avoid a real circular
import: `extractions.py` → `source_text.py` → `transcriptions.py` already
existed in that direction, so a module-level import the other way back would
have been a genuine import cycle.

### What did NOT change

- `start_extraction` itself, its idempotency (`pending`/`processing`/
  `completed`/`failed`), its concurrency handling (claim/lock/finalize), and
  the atomic `ObservationModeration` row creation from Step 18 — all reused
  completely unchanged. Automatic triggering is purely an additional CALLER
  of the exact same function; the function has no idea whether a human or an
  automatic hook invoked it.
- `POST /api/v1/submissions/{id}/extract` still exists and still works
  exactly as before — calling it now almost always just reports the already-
  completed (or already-failed, retryable) result immediately, since
  automatic triggering already ran. This is what the mobile app's existing
  "Understand this report" button calls; it needed **zero mobile app
  changes** for this step — it still shows real status, it just usually
  shows "completed" already instead of "not started yet."
- Transcription itself is still 100% manual/explicit (a guide must still tap
  "Transcribe" for a voice note) — only extraction changed.

### Known gaps

- No minimum-content guard: a two-word test note now spends a real Claude
  API call automatically, same as a substantive field report. This was a
  deliberate, explicit product decision (accepting the cost/volume
  tradeoff), not an oversight.
- No retroactive sweep: submissions created before this step (with source
  text already available but no Extraction row) are not automatically
  extracted by this change — they still need one manual `POST .../extract`
  each, same as before. Nothing re-scans historical data.

## Notes

- `knowledge_type_config` holds a per-knowledge-type freshness/relevance policy — there
  is no global freshness window anywhere else in the codebase.
- `guide_locations`, `submissions`, and `observations` are raw/historical, append-only
  tables. The derived "current best-known knowledge state" engine is
  `app/services/knowledge_state.py` (Step 10) — it reads these tables at query
  time, it doesn't materialize or cache a separate "current state" table.
- Routes/route segments are intentionally not modeled — the system is location-first,
  not trek-first.
- There's no automatic dev data seeding on startup. Use the curl workflow above (create
  guide → submit locations → query) to build test data on demand.
- `GEOGRAPHIC_CONTEXT_RADIUS_METERS` (app.core.config) is unrelated to each
  `knowledge_type_config.geographic_relevance_radius_meters` — the former controls
  "is this known place near this coordinate at all" (used by
  `geographic_context.py`), the latter controls how far an observation of one
  specific knowledge type can be considered relevant (used by
  `knowledge_state.py`, Step 10). Never conflated.
- `guides.client_guide_id`, `submissions.client_submission_id`,
  `submissions.client_audio_id`, and `guide_locations.client_location_id` are all
  nullable, unique-indexed columns holding a caller-generated stable id (the
  mobile app's local UUID). They exist purely to make guide/submission/audio-
  attachment/location creation safely retryable from an unreliable network — see
  `mobile/README.md` for the full outbox design these support.
- Step 9 (LLM structured extraction) deliberately does NOT implement: knowledge
  freshness/staleness/gap detection or ranking, question generation, report
  generation, embeddings, pgvector, semantic/vector search, RAG, or any
  background worker/queue (no Redis, no Celery — same constraint as Step 8).
  Step 9 only *writes* `observations` rows with correct
  `knowledge_type_id`/`geog`/`observed_at`; it doesn't read
  `knowledge_type_config`'s freshness/relevance policy at all — that's Step 10.
  Extraction also never automatically triggers on transcription completion or
  submission creation — always an explicit `POST .../extract`, matching Step
  8's transcription trigger discipline. **Since Step 19 this is no longer
  true** — extraction is now triggered automatically; see
  [Automatic extraction triggering (Step 19)](#automatic-extraction-triggering-step-19).
  Left here unedited otherwise as an accurate record of Step 9's own scope
  at the time it was written.
- Step 10 (knowledge state) reads `freshness_window_hours` and
  `geographic_relevance_radius_meters` for the first time, but deliberately
  does NOT implement: gap ranking/prioritization, natural-language question
  generation, any LLM call, embeddings, pgvector, semantic search, RAG, or any
  background worker/queue. It also does not use `aging_threshold_hours` —
  that field exists on `knowledge_type_config` but nothing in this codebase
  reads it yet; this step's spec asked only for a 3-state
  fresh/stale/missing model off of `freshness_window_hours`, not a finer-grained
  aging tier, so no code was written against a field with no defined behavior
  yet rather than guessing one. Knowledge state is computed live, on every
  request, directly from `observations` + `knowledge_type_config` — nothing is
  cached, materialized, or pre-computed.
- Step 11 (gap ranking + guide selection) also still does NOT use
  `aging_threshold_hours` (same reasoning as Step 10 — no defined semantics
  exist for it anywhere). It deliberately does NOT implement: natural-language
  question generation, any LLM call, question/assignment/task persistence,
  guide notifications, a mobile question inbox, polling, WebSockets, push
  notifications, or any background worker/queue. `default_priority`'s
  direction (higher = more important) is this step's own explicit,
  centralized interpretation — not something the database or any prior step
  documented — see `app/services/knowledge_decisions.py`. Ranked decisions are
  computed live on every request, exactly like Step 10 — nothing is cached or
  persisted.
- Step 12 (question generation + assignment) is the first step where an LLM
  produces guide-facing text, but it deliberately does NOT implement: an
  answer workflow (guides responding to questions — `QuestionAssignment.
  answered_at`/`'completed'`/`'active'`/`'cancelled'` exist in the schema but
  no code sets them), reassignment, guide notifications (push/SMS/etc.),
  a mobile question inbox with polling/WebSockets, any background worker or
  queue, automatic question generation (always an explicit
  `POST /api/v1/questions`, matching Step 8/9/11's trigger discipline), or
  `aging_threshold_hours`-based logic (same reasoning as Steps 10–11 — no
  defined semantics exist for it anywhere in this codebase).
- Step 13 (guide answer workflow) closes the Step 12 loop but deliberately
  does NOT implement: the `active` assignment status (still reserved, see
  "Assignment state transitions" above), reassignment, guide notifications,
  answer editing/re-answering, answer review/moderation, automatic extraction
  triggering on answer submission (extraction remains a separate, explicit
  `POST .../extract`, exactly as for every other submission type — this step
  does not change when/how extraction runs), any background worker/queue, or
  `aging_threshold_hours`-based logic (same reasoning as Steps 10–12).
- Step 14 (knowledge aging) finally gives `aging_threshold_hours` real
  semantics (see "Knowledge aging" section above) but deliberately does NOT
  implement: automatic/background extraction (the answer → extraction →
  observation flow is still triggered only by the existing explicit
  `POST .../extract`, unchanged since Step 9/13), reassignment, answer
  editing/re-answering, review/approval workflows, notifications of any
  kind, embeddings, vector search, or RAG. No schema/migration changes were
  needed or made.
- Step 18 (admin dashboard) adds moderation as a SIXTH independent state
  machine (`observation_moderation.status`) and is careful never to conflate
  it with any of the other five (`sync_status`, `Transcription.status`,
  `Extraction.status`, `Question.status`, `QuestionAssignment.status`) —
  "AI extracted it" / "transcription succeeded" / "the guide submitted it" /
  "knowledge is fresh" are none of them the same claim as "an admin approved
  it," and none of the existing five tables gained a column or changed
  meaning because of this step. It deliberately does NOT implement: real
  per-admin accounts/sessions, automatic conflict/duplicate detection, a
  public-facing API (the boundary is established, not built), moderation
  history/audit trail beyond the current decision, or any change to mobile
  capture/sync/transcription/extraction/question/answer behavior.
